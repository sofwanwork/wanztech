# Development Lessons

- **HTML2Canvas Visibility Quirk**: Never trust `html2canvas` to correctly paint elements positioned at `-9999px` out of the browser viewport. However, **never physically move** the hidden element into the active viewport using hacks like `position: fixed` and `z-index: 9999` before capturing, as this causes the enormous element to flash/spill visually across the user's screen during the 100ms it takes to snapshot. Instead, leave the real element strictly behind `-9999px` and use the `html2canvas` `onclone` Hook to safely target the cloned iframe sandbox element (`clonedDoc.getElementById`), modifying the inner cloned `style.position` without touching the real user DOM.
- **Balancing Quality vs File Size in jsPDF**: Increasing `html2canvas` `scale` (e.g., from `2` to `3` or `4`) sharply enhances HD rendering for text, but bloats file sizes organically. To offset this penalty when writing the PDF via `jsPDF`, never use `image/png` if lossless quality isn't strictly required. Use `image/jpeg` with `.toDataURL('image/jpeg', 0.7)` and inject the image natively to the PDF using the `'FAST'` alias (`pdf.addImage(imgData, 'JPEG', 0, 0, pdfWidth, pdfHeight, undefined, 'FAST')`). This results in a much smaller output byte-count but retains the sharpness of the original 3x scaled text.
- **jsPDF White Borders (Sub-pixel scaling)**: Browsers round element dimensions natively. This creates cases where a generated PDF will exhibit a microscopic 1px white border at the bottom/side. To completely eliminate this, lock the `html2canvas` render state to `scrollY: 0` and `scrollX: 0`, and explicitly add a `+2` offset mapping to the target jsPDF rendering height/width (`pdf.addImage(..., pdfWidth + 2, pdfHeight + 2)`).
- **Dual Auth Flow Awareness**: KlikForm supports TWO Google integration methods — OAuth ("Connect with Google") and Manual Service Account keys. Before modifying any Google-related UI, always check which flow the feature belongs to. The Google Sheet URL + Copy Service Email button in the builder is specifically for manual key users only, not OAuth users.
- **Next.js 16 Proxy Migration**: `middleware.ts` is deprecated in Next.js 16 to distinguish route interception from traditional Express middleware. The file must be renamed to `proxy.ts` and the main exported function must be `export async function proxy(...)`.
- **Handling Third-Party Hydration Mismatches**: Browser extensions frequently inject arbitrary attributes (e.g., `data-jetski-tab-id`) into the `<html>` or `<body>` tags before React finishes hydrating. This causes a hard hydration mismatch error in strict mode. Always apply `suppressHydrationWarning` to the root `<html>` and `<body>` tags in `app/layout.tsx` to safely ignore these uncontrollable third-party mutations.
- **Radix UI Hydration with Next.js App Router**: When using UI components that rely heavily on `useId()` for internal accessibility linkages (like shadcn's `NavigationMenu`), placing them directly inside deeply nested Server Components (like `app/page.tsx`) can trigger random "Hydration Mismatch" errors because the server-generated IDs may not align perfectly with the client's initial render tree. To resolve this, always extract complex interactive UI components into a dedicated `"use client"` component boundary to isolate their hydration lifecycle.
- **`bg-clip-text` Descender Clipping**: CSS `background-clip: text` with `text-transparent` clips the gradient to the text paint area, which on large headings (5xl+) cuts off *descender* strokes of letters like "g", "y", "p". Always add explicit `pb-4` (padding-bottom) on gradient text headings to extend the clipping box past the descender line.
- **Deceptive 42P01 PostgREST Errors (search_path mutation)**: If Supabase suddenly throws an `Error 42P01: relation "table_name" does not exist` on a table that you **know** exists and has correct RLS policies, it is highly likely that a Postgres Trigger function attached to that table has a broken `search_path`. Using Supabase's Security Advisor recommendation to patch functions with `ALTER FUNCTION ... SET search_path = ''` will intentionally "blind" the function from finding tables in the `public` schema unless they are explicitly prefixed (e.g., `public.forms`). If the trigger function is built without schema prefixes, the `search_path = ''` restriction causes the entire `INSERT/UPDATE` operation to fail with a misleading 42P01 error indicating the primary table (not the trigger's internal reference) is missing. Revert with `ALTER FUNCTION ... RESET search_path;` and `NOTIFY pgrst, 'reload schema'` to restore functionality.
- **PostgREST Schema Caching**: When adding new columns directly via SQL migrations to a live Supabase database, the changes are not immediately visible to the PostgREST API layer. Any API upserts containing the new columns will fail with `42P01 relation does not exist`. Always execute `NOTIFY pgrst, 'reload schema'` immediately after schema alterations to flush the stale API cache.
- **Always sync feature lists across all surfaces.** When updating pricing features, remember there are TWO places to update: `app/pricing/page.tsx` (public pricing page) AND `components/pricing-modal.tsx` (in-dashboard upgrade modal). Missing one causes inconsistency between what the public sees and what logged-in users see.
- **CSS `flex-1` placement matters in card layouts.** When pricing/plan cards have different content lengths, putting `flex-1` on the top section (header/price area) creates ugly empty gaps. Always apply `flex-1` to the bottom section (feature list + button) so buttons align at the bottom and the price section stays compact.
- **Turbopack cache can cause 404s unexpectedly.** If a route suddenly returns 404 even though `page.tsx` exists, restart the dev server first. If that doesn't work, delete the `.next` folder and restart. This is a known Turbopack caching issue with Next.js 16.
- **KlikForm complete feature set (marketing reference):** Online Forms (Google Sheets integration), Dynamic QR Code Generator, URL Shortener, E-Certificate Generation (auto-generated & emailed to participants), Certificate Verification System (unique serial number + QR code for authenticity).
- **Public-facing queries must bypass RLS**: Any Supabase query that serves public/unauthenticated users (e.g., `getCertificateTemplatePublic`) must use `createAdminClient()` (service role), NOT `createClient()` (auth-aware SSR). The auth-aware client respects RLS policies gated on `auth.uid()`, which is null for unauthenticated visitors — silently returning empty results. This causes features to appear broken on mobile/logged-out devices while working perfectly for the logged-in owner on desktop.
- **Use COUNT queries for limit checks, not SELECT ***: When checking if a user has exceeded a resource limit (e.g., max certificates), never do `getCertificateTemplates().length` which fetches ALL rows including heavy JSON columns. Instead, use a dedicated count function with `select('*', { count: 'exact', head: true })` which returns only the count without transferring any row data. This is especially important when rows contain large payloads like certificate element arrays.
- **Google Sheets Header Syncing (Data Dropping)**: When writing data to Google Sheets using `google-spreadsheet`, `sheet.addRow(data)` relies entirely on the pre-existing header columns to map the object keys. If a user adds a new field to their dynamic form, the payload will contain new keys, but the sheet will quietly ignore them if the new headers don't exist in row 1. To solve "missing data" upon form updates, always explicitly diff the incoming keys against the current `headers`, and update the sheet with `sheet.setHeaderRow([...headers, ...missingHeaders])` before appending the row.
- **react-joyride V3 Stacking Contexts**: When using `react-joyride` V3, the portal mounts directly to `document.body` by default. Attempting to force the overlay `zIndex` higher than a sticky header by overriding Joyride's internal `styles` will often cause the overlay to cover its own tooltip because they share the same stacking container. Instead of battling internal portal z-indexes, dynamically downgrade the sticky header's z-index (e.g. `runTour ? "z-0" : "z-10"`) while the tour is active, allowing Joyride's default `z-100` portal to naturally cover it.
- **react-joyride V3 ScrollOffsets**: The `scrollOffset` property is no longer accepted as a top-level prop on the `<Joyride>` component in V3. Passing it there will be silently ignored, causing the browser to scroll targets tight to the top of the viewport (offset `20px`), causing them to get trapped under sticky headers. You must explicitly map the `scrollOffset` property onto the individual items inside the `steps` array (e.g. `steps.map(step => ({ ...step, scrollOffset: 150 }))`).
- **Stale lint/build artifacts mislead**: When committed, files like `lint_output.txt` or `build_output.txt` look authoritative but are snapshots from a different machine/branch state. They can show problems that no longer exist (or hide problems that do). Always re-run `npm run lint` / `npm run build` directly before drawing conclusions. Add `*_output.txt`, `build-log.txt`, `tsconfig.tsbuildinfo` to `.gitignore` and untrack them via `git rm --cached`.
- **Optional dependencies via dynamic import need runtime string syntax**: Writing `await import('@upstash/redis').catch(() => null)` still causes TypeScript to fail the build with "Cannot find module" because the literal string is statically analyzed. Workaround: assign the module path to a variable first (`const m = '@upstash/redis'; await import(m).catch(...)`). The module stays optional at runtime and the TS check passes.
- **Next.js 16 `proxy.ts` IS the path forward**: Earlier internal lessons (now revised) suggested `proxy.ts` was "ignored" by Next.js 16. That was wrong — the migration failed for an unrelated reason. The official codemod (`npx @next/codemod@canary middleware-to-proxy .`) is just a file rename + function rename. After migrating, the build's deprecation warning disappears.
- **Sentry should be conditional in build config**: Hard-wrapping with `withSentryConfig` causes failures on PR previews / contributors who don't have `SENTRY_AUTH_TOKEN`. Wrap conditionally: `export default (DSN && AUTH_TOKEN) ? sentryConfig : nextConfig`. Inside `sentry.*.config.ts`, gate `Sentry.init()` on the DSN being present.
- **Production trace sampling**: `tracesSampleRate: 1` (100%) in production explodes Sentry costs. Use `process.env.NODE_ENV === 'production' ? 0.1 : 1` so dev gets full visibility while prod samples 10%.
- **Three places to update when changing rate limiting**: `lib/rate-limit.ts` (core), `actions/forms.ts` (form submission), `actions/certificates.ts` (cert verification). Don't introduce new ad-hoc `Map<string, ...>()` instances per file — use the shared `checkRateLimit(ip, RATE_LIMITS.<bucket>, 'name')` API. Each bucket is namespaced via the third arg so different features don't share counters.
- **Schema-qualify in `SET search_path = ''` functions**: When applying Supabase Security Advisor's `search_path = ''` to trigger/SECURITY DEFINER functions, every table reference in the function body MUST be schema-qualified (e.g. `public.forms`, `auth.users`). Without the prefix, the empty search_path causes `42P01 relation does not exist`. The proper fix is to update function bodies, not to `RESET search_path` (which silences the warning by reintroducing the vulnerability).
- **Server Action modules: every export must be async AND types can't be re-exported**: Files marked `'use server'` are treated as Server Action modules by Next.js 16 + Turbopack. Synchronous helpers (`function aggregate(...)`) cause "Server Actions must be async functions". Re-exporting types via `export type { Foo }` from a server-action file silently builds in some cases but fails under Turbopack with "Export Foo doesn't exist in target module". Solution: keep pure helpers + types in a separate `lib/<feature>/` file; server-action wrappers import from there. Never re-export types from a `'use server'` module — import them directly from the lib path.
- **Privacy-first analytics**: When storing visitor analytics in a SaaS multi-tenant app, hash IPs with a daily-rotating salt (`SHA256(ip + YYYY-MM-DD + secret)`). This gives accurate per-day unique-visitor counts without ever storing raw PII or enabling long-term cross-day tracking. Coarse-grain User-Agent into device family (mobile/desktop/tablet/bot) rather than storing the full string. Insert via service role from the public client (since visitors are anonymous), but force RLS owner-only SELECT and denormalise `user_id` onto each event row so the auth predicate is cheap.
- **`server-only` breaks Vitest**: The real `server-only` package throws on import outside an RSC, which is correct in production but blocks Vitest (Node) from loading any storage/action helper marked with it. Map `'server-only'` in `vitest.config.ts` `resolve.alias` to an empty stub file (`tests/__mocks__/server-only.ts` with `export {}`). This keeps the production guard and lets unit tests import server-tagged modules to test their pure helpers.
- **Zod v4 uses `.issues`, not `.errors`**: When catching `z.ZodError`, read `err.issues[0]?.message`. The old `.errors` field was renamed and the v4 type doesn't expose it. Build-time TS error: `Property 'errors' does not exist on type 'ZodError<unknown>'`.
- **Add new types to BOTH `lib/types/<file>.ts` AND `lib/types/index.ts`**: Components import from `@/lib/types` (the barrel), so adding a type only to the source file passes lint but fails `next build` typecheck for any consumer. When introducing `ConditionOperator`, `ConditionRule`, `EditLinkSettings` etc., re-export them from the barrel in the same commit.
- **Reusable secrets need encryption + masking discipline**: For per-tenant secrets (webhook signing keys, API tokens), keep two read paths in storage: a `listForOwner(...)` that returns masked dots so the secret never leaves the server in plaintext, and a `listForDispatch(...)` that decrypts only at the moment of use. UI's "rotate" button should regenerate + immediately reveal once (then dots again on next render). This way a leaked DB dump is useless and the UI never has to re-fetch the plaintext.
- **Bulk client-side rendering needs two `requestAnimationFrame` waits**: When looping React state changes through a hidden renderer for capture, one `await nextFrame()` lets React commit but the browser may not have painted the new computed styles yet. Two consecutive `requestAnimationFrame` waits gives one frame for commit and one for paint, after which html2canvas reads accurate dimensions and fonts.
- **CSV "empty" check must trim**: A CSV string of `'   '` is non-empty but produces a single empty header row when split. Guard with `if (!src.trim())` not `if (!src)` so whitespace-only inputs return clean empty headers + rows.
- **Re-key snapshot from label to field id when prefilling**: Google Sheets are keyed by field label (the human-readable header), but `PublicFormClient`'s state is keyed by field id. When loading a snapshot for the edit-link flow, walk `form.fields` and rebuild `initialValues[field.id] = snapshot[field.label]`. Failing to re-key shows a blank form even though the snapshot is correct.
- **Robots-noindex magic-link routes**: Edit-link and other token-based public URLs must set `metadata.robots: { index: false, follow: false }` so search engines don't crawl, archive, or expose them in cached results. RLS protects the data but a leaked URL in a search index is a separate, real problem.
- **Triggers and Database Constraints (NOT NULL/Incorrect columns)**: When writing or updating PostgreSQL trigger functions that automatically seed other tables (e.g. `public.usage` on user signup), verify that:
  1. The column names in the `INSERT` match the actual table schema exactly (e.g. `forms_created` vs `total_forms`).
  2. All `NOT NULL` columns that lack default values (e.g. `month DATE NOT NULL`) are populated with valid values in the trigger's query (e.g. `date_trunc('month', current_date)::date`).
  Failing to do so will cause the signup database transaction to abort, showing a generic "database error" to the user and preventing registration.
- **Dual-Method Integration Validation (OAuth vs Service Account)**: When implementing features that gate resource creation or modification on configured integrations (such as Google Sheets integration in `createFormAction`), always ensure that you check for *either* method. Checking only for manual Service Account fields (`googleClientEmail` + `googlePrivateKey`) will inadvertently block users who chose the recommended OAuth path (`googleAccessToken`), forcing them to configure settings they do not need.
- **Shared PostgreSQL Trigger Functions (Trigger Target vs Column Fields)**: If you repurpose a trigger function (such as `generate_short_code()`) to target a different table (e.g. from `public.forms` to `public.short_links`), and change the column fields it references (e.g. from `NEW.short_code` to `NEW.slug`), you must explicitly drop/recreate any old triggers executing this function on the old tables. Otherwise, the old table inserts/updates will trigger the updated function, fail on the missing columns (throwing `record "new" has no field "slug"`), and abort the transaction. Keep trigger functions scoped to their respective tables (e.g., `generate_form_short_code()` for `forms` vs `generate_short_code()` for `short_links`).
- **Server-side auth checks block Static Site Generation (SSG)**: Reading `cookies()` or executing server-side Supabase auth checks (like `supabase.auth.getUser()`) inside page components forces Next.js to render them dynamically (SSR) at runtime. For marketing pages (landing, pricing, about, product specs), this causes serverless cold starts and latency. Instead, use a client-side component (like `LandingHeaderAuth`) that queries auth state on mount, leaving the static page body to build statically and be cached on the Edge CDN.
- **Vercel Serverless Function Regions**: Vercel deploys serverless functions to Washington D.C. (`iad1`) by default. If the database is hosted in Singapore (`ap-southeast-1`), this adds ~250ms latency per query. Explicitly configure `"regions": ["sin1"]` in `vercel.json` to place serverless execution close to the database.


- **Escape HTML for any respondent-controlled value injected into emails**: Confirmation/notification email templates that embed user-submitted values (answers, custom messages, form title) into the HTML body must HTML-escape them (`&`, `<`, `>`, `"`, `'`). Without escaping, a respondent can inject markup/`<script>`/broken table cells into the email — a stored-content injection vector. Use a small `escapeHtml()` helper and apply it to every interpolated untrusted value. (Note: `getNewSubmissionEmail` owner-notification template predates this rule and still interpolates raw values — a separate fix.)
- **Respondent email confirmation reuses the edit-link pattern exactly**: When adding per-form settings gated on an email field (respondent confirmation, edit-link), follow the established recipe: jsonb column on `forms` (avoid column proliferation) + type in `lib/types/forms.ts` re-exported from the barrel + 2× fromRow mapping (getFormById AND getFormByShortCode — they're duplicated) + 1× toRow in saveForm + fire-and-forget dispatch block in `submitFormAction` (try/catch, never fail submission) + builder card mirroring `EditLinkCard` + email-value resolved via `dbData[field.label]` (dbData is keyed by label, not id).
- **Editing the type barrel: don't drop sibling exports**: `lib/types/index.ts` mixes `export type {...}` blocks with a value export (`export { TIER_LIMITS }`). When adding a new type export, append it — don't replace a block in a way that removes the trailing `TIER_LIMITS` value export, or every `TIER_LIMITS` consumer breaks at build time. (Nearly did this adding audit types.)
- **Two-layer enforcement for consent/gating (PDPA)**: A consent checkbox in the client is UX only — it can be bypassed by calling the Server Action directly. Always enforce the same gate server-side in `submitFormAction` (reject when `pdpaSettings.enabled` and the consent flag isn't exactly `'true'`). Keep the predicate in a pure module (`lib/forms/pdpa.ts`) so both sides and the tests share one source of truth.
- **Layout-only field types must be excluded from data paths**: A new non-input field type (`pagebreak`, like `separator`/`image`) is still returned by `form.fields`. If it leaks into `visibleFields` it gets validated, appended to FormData, and creates a junk column in Google Sheets. Filter it out of `visibleFields` (`f.type !== 'pagebreak' && isFieldVisible(f)`) while still letting `splitIntoPages` use it as the page delimiter.
- **Multi-page without a schema change**: Implement pages by inserting a `pagebreak` delimiter field into the existing `fields` array rather than adding a new DB structure. `splitIntoPages` drops the markers and yields page buckets; forms with zero pagebreaks naturally collapse to a single page (backward compatible, no migration). Skip pages whose every field is hidden by conditional logic via `findAdjacentNonEmptyPage` so navigation never lands on a blank page.
- **Guard Enter-key submit on multi-page forms**: A form with `onSubmit` will fire on Enter even when the visible primary button is a type="button" Next. In `handleSubmit`, short-circuit `if (multiPage && !isLastPage) { goToNextPage(); return; }` so Enter advances the page instead of submitting partial data.
- **Audit tables are append-only from the client**: Give `audit_logs` an owner-only SELECT RLS policy and NO insert/update/delete policy. Writes go exclusively through the service-role admin client inside `logAudit()`. This makes the trail tamper-proof from the browser while still readable by its owner. Log meaningful, low-frequency events (create/delete) — never per-keystroke autosave (`updateFormAction`), which would flood the log.
- **Never read layout (`offsetWidth`/`getBoundingClientRect`) inside a render `.map()`**: In the certificate builder, `const scale = canvasRef.current.offsetWidth / template.width` lived inside `template.elements.map(...)`, so it read layout once PER element PER render. During drag/resize (rapid setState) this triggers repeated synchronous "forced reflow" / layout thrashing (Chrome `[Violation] Forced reflow … took NNms`). Fix: track the container size in state via a `ResizeObserver` (its callback delivers `contentRect` without forcing reflow) and compute the derived value ONCE per render, not per item. Bonus: the value (font scale) now also reacts to window/container resize, which the render-time `offsetWidth` read silently failed to do. Reading layout inside a discrete event handler (e.g. `getBoundingClientRect` in `onMouseMove`) is fine — it's one read per event, not per render.
- **Deploying via `vercel --prod` from the working dir bypasses git entirely**: It uploads local files, so production can silently drift ahead of the `master`/production branch (no commits, no history, no rollback). If a Vercel project is git-connected, prefer `git push` to the production branch to auto-deploy — that keeps git == production and gives preview deploys + an audit trail. Periodically check `git log master..HEAD` to catch drift.
- **Unit-testing Supabase storage modules without a live DB**: mock `@/utils/supabase/server` (`createClient`, async) and `@/utils/supabase/admin` (`createAdminClient`, sync) with `vi.hoisted` + `vi.mock`. Build a chainable query-builder mock where each chain method returns the builder, `.single()` returns a configurable promise, and the builder is *thenable* (`then(resolve){resolve(result)}`) so `await from().select().eq().order()` resolves too. Mock `@/lib/encryption` to assert encrypt-on-write / decrypt-on-read without a real key. Lets you verify query scoping, row mapping, secret masking, and ownership checks deterministically.
- **Label-control association is the most common form a11y gap**: A visible `<Label>` that only sits *near* an input (no `htmlFor`/`id`) is not programmatically associated — screen readers don't announce it (WCAG 1.3.1/4.1.2). For simple inputs use `htmlFor`/`id`; for composite widgets (radio/checkbox groups, custom selects) give the label an `id` and point the group/trigger at it via `aria-labelledby` + `role="group"`. Put required indicators behind `aria-hidden` and add an `sr-only` word so the asterisk isn't read as punctuation.
- **"Bug still there after deploy" is often a stale browser cache, not the code**: A user reported multi-page "Next auto-submits" persisting after fixes. The code was correct AND triple-protected (Next is `type="button"`, `handleSubmit` returns early on non-final pages, and `preventDefault` on the Next click) — submit on a non-final page was provably impossible. Root cause was the browser serving the previous JS bundle. Before chasing a phantom code bug across multiple deploys, first confirm the user has hard-refreshed (Ctrl+Shift+R) / tested in Incognito, and verify the latest production deployment is `Ready` and matches the latest commit. After a real hard refresh the multi-page nav (Next/Back + "Page X / Y" + Submit only on the last page) worked correctly.
- **Robust Column/Header Matching & Guarding Fallbacks**: When parsing dynamic spreadsheets (e.g. Google Sheets), use word-boundary regexes like `/\bkp\b/` or `/\bic\b/` rather than strict matches or broad substrings. This accommodates compound headers (e.g., `IC/Passport`, `No. KP/Pasport`) without matching letters inside unrelated fields (e.g., `office`, `timestamp`). Additionally, never fall back to using the user's search query (like their email input) in templates if the actual target field (like `ic`) was missing/undefined, as this leads to rendering email addresses on documents where the IC number is expected. Use a conditional check to guard fallbacks.
- **Write external-API data locally FIRST, sync remotely after**: Any submission that must end up in a slow/flaky third-party system (Google Sheets, CRM, webhook) should be persisted to your own DB first, then synced asynchronously (`after()` in Next.js 15+/16, plus a retry cron). The old pattern (remote write on the critical path) loses data on remote failure AND blocks the user on remote latency. Track sync state on the row (`pending`/`synced`/`failed` + partial index) so retries are cheap and idempotent — the unique `submission_id` doubles as an idempotency key that swallows double-submits.
- **`after()` snapshots: capture request context before the callback**: Anything read from `headers()`/`cookies()` must be snapshotted into plain variables BEFORE scheduling `after(async () => ...)`. Inside the after-callback the request context is finalizing and reads can fail or return stale values. Same for any object you `let`-rebind later (e.g. `accessToken`) — copy to a `*Snapshot` const and close over that.
- **Webhook handlers must use the service-role client**: A provider webhook (BCL, Stripe...) arrives with NO user cookies. `createClient()` (anon) under owner-only RLS silently finds nothing — the handler 404s on data that exists. All webhook DB reads/writes go through the admin client; authenticity comes from the HMAC signature, not from session identity.
- **Payment idempotency: mark processed in the same write as the grant**: Set `processed_at` in the SAME update that flips status to completed, BEFORE upserting the subscription/emails. Checking `status === 'completed'` alone is unsafe (pre-existing completed rows from partial failures must remain re-processable); checking after the grant is unsafe (crash between grant and marker = double grant). Replay response: 200 `{duplicate:true}` — never 4xx, or the provider keeps retrying a permanently "failing" endpoint.
- **Postgres unique-violation code is 23505**: supabase-js surfaces it as `error.code`. Use it to distinguish "duplicate idempotency key — swallow" from "real insert failure — surface to user". Pattern: `insert()` returns `{error:{code:'23505'}}` → treat as already-done success.
- **Backfill idempotency markers when adding them to live tables**: A new `processed_at` column starts NULL on all existing rows. Without `UPDATE ... SET processed_at = now() WHERE status='completed'` in the migration, the first replayed webhook after deploy double-processes every historical payment.
- **One pricing constant file, everywhere**: price/amount/description strings drift when hardcoded in the checkout route, the marketing page, the in-app modal, AND a constants file. Keep a single `PRO_PRICE` object (amount as number for gateways + display strings) and import it from all four. Test asserts `display === `RM ${amount}`` so a mismatch fails CI.
- **Re-using the client's conditional evaluator server-side closes the required-field loophole**: extracting submission validation into a pure module (`validateSubmission`) that calls the SAME `evaluateConditional` as the public form means "required but hidden by logic" is allowed server-side exactly when the client hides it. Re-key the label-keyed payload to field ids (`byId`) before evaluating — conditions reference field ids, but FormData arrives keyed by label.
- **Theme-Contextual Button Styling & Contrast Guards (Glassmorphism / Outline)**: When allowing users to pick both background themes (light vs dark) and button appearance styles (e.g., Glassmorphism, Outline Border), never concatenate static translucent classes (like `bg-white/10 border border-white/20`) with theme classes. On light backgrounds (e.g. `Minimal Light` with `#f1f5f9`), `bg-white/10` is virtually invisible, and if a highlight state applies `text-white`, the text becomes pure white `rgb(255,255,255)` on a white/light surface, making it completely unreadable. Always use a contextual resolver function (like `getBioButtonClass(theme, style, isHighlight)`) that adapts both background opacity and text color: light themes must enforce dark, high-contrast text (`text-slate-900` / `text-slate-950`) with frosted milk glass (`bg-white/70` to `bg-white/90`), while dark themes use white or theme-accent text with translucent glass.
- **Narrow Dialogs & `DialogFooter` Overflow Collision**: Shadcn's `DialogFooter` defaults to `sm:flex-row sm:justify-end`. If a narrow modal (like `sm:max-w-xs` or `sm:max-w-sm` QR/Share dialogs) contains multiple buttons that have `w-full` and `shrink-0` (the default in shadcn button variants), the combined button widths will easily exceed the narrow dialog width. Because `sm:justify-end` right-aligns flex items, the first button is pushed outside to the left of the dialog box into the open screen area. In narrow dialogs, never use `DialogFooter` with `sm:flex-row`; use `<div className="grid grid-cols-2 gap-2 w-full">` or stack them vertically with `flex-col`, ensuring both buttons fit inside the card container.
- **SelectTrigger `w-fit`, `flex` vs `line-clamp`, and Dialog Grid Expansion**: Shadcn Tailwind v4's default `SelectTrigger` uses `w-fit` and `*:data-[slot=select-value]:flex *:data-[slot=select-value]:line-clamp-1`. When rendering long option values (such as lengthy form titles), `display: flex` breaks `-webkit-box` line-clamping, and `w-fit` allows the trigger to expand to the natural single-line width of the text (~1000px). Penyelesaian: Kesan `naturalWidth / naturalHeight` imej secara dinamik menerusi acara `onLoad` imej (atau manfaatkan metadata `page.aspectRatio`). Kira dimensi kontena bingkai pentas berasaskan nisbah sebenar yang dikesan tersebut (`detectedRatio || page.aspectRatio || defaultRatio`) supaya sempadan dokumen bertepatan tepat dengan imej tanpa sebarang jurang jalur putih.
- **Single-Page Edge-to-Edge Flush Sizing & Margin Elimination**:
  1. *Elakkan Pengurangan Kelebaran Tiruan*: Dalam mod 1 Halaman (Single Page) terutamanya untuk risalah landskap atau slaid digital, jangan mengenakan pemotongan kelebaran sebarangan seperti `targetW > availW * 0.94`, `maxWidth: '96vw'`, atau menolak ruang `availW = containerWidth - 24`. Pengurangan bertingkat ini mengecilkan saiz paparan sebanyak 10% hingga 15%, lalu meninggalkan jurang kosong (gap ~50px) di sisi kiri dan kanan skrin telefon/komputer riba. Sebaliknya, benarkan `targetW` memanfaatkan 100% ruang `singleAvailW = containerDimensions.width`.
  2. *Ketinggian Anjal & Pengesanan Bucu Sempadan*: Penolakan ketinggian `availH` mestilah anjal (`containerHeight - 44` untuk landskap) kerana elemen `main` pemapar lazimnya sudah pun mengecualikan palang atas header. Sekiranya kelebaran dokumen hampir memenuhi skrin (dalam lingkungan 64px) dan ketinggian masih muat, luaskan dokumen secara terus kepada `targetW = singleAvailW` supaya gambar melekat rapat ke tepi (*edge-to-edge*).
  3. *Penyesuaian Visual Kontena Edge-to-Edge*: Apabila gambar melebar rapat ke tepi skrin (`bookWidth >= containerDimensions.width - 4`), tukar kelas bingkai daripada `rounded-xl sm:rounded-2xl` kepada `rounded-none`, dan buang bayangan tulang belakang (`spine crease shadow`) di sebelah kiri bagi dokumen landskap kerana risalah grafik/slaid adalah helaian rata dan bukannya novel berjilid.
- **FOUC Layout Shift & Mount Flash Prevention on Page Refresh**:
  1. *Punca Asal Lompat Saiz ("kenapa bila refresh dia macam ni dulu")*: Pada komponen klien yang dimensinya bergantung kepada ukuran viewport/kontena (`containerRef.current.clientWidth/clientHeight`) dan pengesanan nisbah imej (`img.naturalWidth/naturalHeight`), render permulaan (SSR dan first paint) terpaksa bergantung kepada nilai rujukan deterministik (cth: `1024x768`) dan nisbah lalai (A4 1.414). Apabila pengguna menekan muat semula (refresh / F5), pelayar merender pas pertama dengan nilai lalai ini dahulu sebelum `ResizeObserver` membaca saiz sebenar dan sebelum imej selesai dimuat turun. Perbezaan ini menghasilkan kelipan saiz visual (FOUC / layout snap) di mana kontena kelihatan kecil/bermargin sebelum tiba-tiba mengembang.
  2. *Pencegahan Menerusi `isMounted` & Pengekstrakan Cache Segera*: Jangan paparkan kontena yang belum selesai diukur pada kelegapan 100%. Mulakan komponen dengan state `isMounted = false` dan pasang kelas `transition-opacity duration-200` bersama `opacity-0 pointer-events-none`. Di dalam `useEffect` pertama: (a) Lakukan `updateSize()` serta-merta; (b) Imbas semua elemen `img` dalam kontena untuk mengekstrak `naturalWidth / naturalHeight` bagi imej yang telah sedia ada di dalam cache pelayar (`img.complete`); (c) Aktifkan `setIsMounted(true)`. Kaedah ini memastikan dokumen hanya memudar masuk (*fade-in*) ke skrin selepas saiz sebenar dan nisbah aspek telah siap dikira sepenuhnya, menghapuskan sebarang gegaran atau lompatan saiz.
- **Default Visual Theme Alignment Across System Layers**:
  Apabila menukar tema lalai produk (seperti menukar tema lalai daripada gelap kepada terang 'Clean Studio'), pastikan perubahan dilaksanakan secara holistik pada 5 lapisan serentak:
  (1) Pemalar tema teras (`DEFAULT_PAMPHLET_THEME: PamphletTheme = 'light'`);
  (2) Lapisan pemetaan storan pangkalan data (`mapPamphletFromRow` dan `createPamphlet` fallback kepada `DEFAULT_PAMPHLET_THEME`);
  (3) Komponen dialog penciptaan klien (elakkan `const theme = 'emerald'` yang dikod keras; gunakan pemalar lalai berpusat);
  (4) Komponen pemapar awam (`PamphletViewer`, `PamphletToolbar`, `ThumbnailsStrip` fallback);
  (5) Pengemaskinian terus pada rekod sedia ada pangkalan data bagi data yang sedang diuji aktif oleh pengguna supaya kesan perubahan dapat dilihat serta-merta tanpa perlu membina semula borang/dokumen dari awal.
- **Balanced Desktop Studio Sizing & Floating Toolbar Clearance Guard**:
  Jangan memaksakan penyesuaian *edge-to-edge* 100% pada skrin lebar komputer desktop/laptop (`targetW = 100%`). Pada skrin beresolusi tinggi (1080p / 1440p) atau nisbah 16:9, regangan 100% lebar menjadikan ketinggian dokumen melonjak secara berkadar sehingga melimpah ke bahagian paling bawah tetingkap. Ini menyebabkan palang navigasi bawah terapung (`absolute bottom-4`) menutupi teks, jadual, dan ilustrasi di bahagian kaki dokumen ("zoom sangat"). Penyelesaian reka letak seimbang:
  (1) Berikan kelegaan menegak minimum 104px (`containerDimensions.height - 108` pada desktop) supaya tapak dokumen berhenti sekurang-kurangnya 30-40px di atas palang navigasi bawah;
  (2) Kenakan had kelebaran santai (`Math.min(width * 0.90, width - 64)`) dan padding pentas `p-2 sm:p-4 md:p-6` agar dokumen kelihatan seperti karya berbingkai anggun di atas kanvas studio galeri dengan bayangan lembut (`shadow-2xl rounded-xl sm:rounded-2xl`);
  (3) Serahkan pembesaran terperinci kepada gestur dwi-klik (1.85x) atau butang zum `[+]` pada toolbar apabila pengguna mahu meneliti teks halus secara khusus.
- **3D Flipbook Lighting & Shadow Elegance (Pencegahan Denyutan / Pulse Artifacts)**:
  Jangan sesekali menggunakan keyframe bayangan melantun seperti `animate={{ opacity: [0, 0, 0.25, 0] }}` atau lonjakan permulaan mendadak `initial={{ opacity: 0.3 }}` pada halaman tapak statik semasa animasi selakan 3D. Perubahan kelegapan mendadak pada muka surat yang sepatutnya pegun menghasilkan ilusi denyutan visual (*visual pulse*) atau kilatan hitam (*strobe flash*) di mata pengguna. Prinsip fizik selakan 3D realistik:
  (1) **Halaman Tapak Kekal Bersih**: Halaman tapak statik tidak memerlukan lapisan bayang buatan yang berdenyut; kedalaman optik sudah mencukupi menerusi bayangan lipatan tulang buku kekal (`spine crease shadow`);
  (2) **Pencahayaan Kertas Lembut & Gradual**: Helaian berputar (`turningLeaf`) hanya memerlukan pencahayaan kelegapan lembut ($\le 0.15$ berbanding $0.35 - 0.40$) menggunakan gradien halus `via-black/5 to-black/15` untuk membayangkan sudut terpesong dari sumber cahaya, dan mencerah kembali secara eksponen ke 0 apabila mendarat rata;
  (3) **Bayangan Helaian Sederhana**: Gantikan `shadow-2xl` (jejari 50px) dengan `shadow-lg` pada helaian berputar bagi mengelakkan sempadan bayangan tebal terpotong (*clipped*) dalam ruang perspektif 3D atau meletup hilang (*pop out*) secara mengejut sebaik sahaja helaian dinyah-lekap pada akhir animasi (t = 520ms).
- **Penghapusan Menyeluruh Punca Pulse & Pop Pada 3D Flipbook**:
  Apabila pengguna melaporkan animasi terasa seperti "keluar macam pulse", semak 5 faktor serentak dan elakkan hanya membaiki lapisan bayang:
  (1) **Bunyi Sintesis Audio**: Sintesis Web Audio API (letusan white noise 80ms) yang dipanggil tanpa syarat akan didengari oleh pengguna pembesar suara/headphone sebagai denyutan bunyi ("pop/pulse") setiap kali klik; sentiasa sekat dengan prop `soundEnabled` (lalai senyap);
  (2) **Animasi Selakan 1 Halaman**: Jangan gunakan animasi luncur sisi `x: '-105%'` dan `opacity: 0` bersama pertukaran imej tapak segera di t=0. Bina selakan kad 3D dwi-muka sejati (*True 3D Double-Sided Card Flip*) yang berputar 180 darjah pada `transformOrigin: 'center center'` dengan muka hadapan (muka surat asal) dan muka belakang (muka surat sasaran) berasingan (`backface-visibility: hidden`). Tapak di bawah kekal memaparkan muka surat asal sehingga tamat pusingan;
  (3) **Perspektif 3D Tinggi (5000px)**: Nilai perspektif 2000px/2500px menyebabkan bucu helaian mengembang sebanyak 25% mendekati kamera ("keluar"), menghasilkan ilusi kembung-kuncup; gunakan `perspective: 5000px` untuk kesan selakan isometrik yang tenang dan rata;
  (4) **Hapuskan Lapisan Tindanan Gelap**: Elakkan lapisan `<motion.div>` yang menganimasikan kelegapan hitam 0 -> 0.15 -> 0 semasa selakan kerana perubahan warna ini dibaca oleh retina sebagai denyutan gelombang hitam;
  (5) **Kunci Nisbah Aspek Dokumen**: Kunci `documentRatio` utama supaya `bookWidth` dan `bookHeight` tidak berubah walau 1 piksel pun sewaktu beralih muka surat, mengelakkan getaran saiz kontena.
- **Pencegahan Garis di Tengah Semasa Animasi 3D Flipbook (Spine Hinge vs Center Axis)**:
  Jangan sesekali menggunakan `transformOrigin: 'center center'` untuk animasi selakan 1 halaman 3D. Putaran 180° pada paksi tengah menyebabkan helaian menguncup menjadi garisan tegak setipis pisau (*knife-thin vertical edge*) tepat di tengah-tengah skrin apabila berada pada sudut 90° (`rotateY: -90deg`), memancarkan garisan pembahagi hodoh pada setiap selakan ("setiap helaian garis akan muncul di tengah").
  Prinsip seni bina selakan tanpa garis tengah:
  (1) **Engsel Tepi Tulang Buku (Spine-Hinged Flip)**: Kunci paksi putaran helaian tunggal pada tepi tulang buku: `transformOrigin: 'left center'`. Helaian berayun dari kanan ke kiri untuk *Next* (`rotateY: 0 -> -85deg`, `opacity: [1, 1, 0]`) dan dari tulang ke kanan untuk *Prev* (`rotateY: -85 -> 0deg`, `opacity: [0, 1, 1]`). Tiada satah yang pernah berserenjang di tengah skrin;
  (2) **Pertukaran Halaman Tapak Tanpa Hentakan**: Semasa selakan *Next*, muka surat sasaran dipaparkan serta-merta di halaman tapak bawah, membolehkan helaian berputar menyingkap muka surat baharu secara lancar tanpa sebarang kelipan atau pertukaran imej mengejut semasa selesai;
  (3) **Sifar Sempadan & Bayang Jahitan Dwi-Halaman**: Pada mod 2 halaman, buang sebarang elemen pembahagi tulang buatan (`w-2 z-40`), hapuskan sempadan dalaman (`border-r-0` dan `border-l-0`), buang `shadow-inner` daripada halaman asas, dan sekat bayangan lipatan tulang kasar bagi dokumen landskap (`!isLandscape`) agar poster/risalah melintang bercantum 100% licin (*seamless*).
- **Togol State Tri-State ('auto' | 'single' | 'double') & Bahaya Boolean Ternary Naif**:
  Apabila mengendalikan state togol yang mempunyai nilai permulaan `'auto'` bersama pilihan eksplisit `'single'` dan `'double'`, jangan sesekali menganggap nilai sebelumnya (`prev`) hanya mengandungi dua kemungkinan dengan menulis `prev === 'single' ? 'double' : 'single'`.
  Jika state bermula dengan `'auto'` dan paparan automatik sedang menghasilkan mod satu halaman (seperti dokumen 2 muka surat atau peranti mudah alih), semakan `prev === 'single'` mengembalikan `false`, lalu memaksa state menjadi `'single'`! Kerana `'single'` dan keadaan awal `'auto'` menghasilkan paparan visual yang sama (1 halaman), klik pertama menjadi "klik mati" (*dead click*) di mana tiada apa-apa berlaku pada skrin. Pengguna terpaksa menekan kali kedua untuk akhirnya mencetuskan pertukaran ke `'double'`.
  Prinsip seni bina togol tri-state kalis klik mati:
  (1) **Togol Berasaskan Status Aktif Semasa**: Nilai keadaan visual sebenar (`isCurrentlyDouble`) di dalam fungsi kemas kini state `setPageSpreadMode((prev) => ...)`: jika sedang memaparkan dwi-halaman, tukar ke `'single'`; jika sedang memaparkan satu halaman (sama ada `'single'` mahupun `'auto'`), tukar ke `'double'`. Ini menjamin klik pertama bertindak balas serta-merta dalam semua mod;
  (2) **Gating Kerelevanan Toolbar**: Jangan paparkan butang togol mod spread dwi-halaman jika dokumen hanya mempunyai 1 muka surat (`totalPages >= 2`), kerana dokumen helaian tunggal tidak mempunyai muka surat kedua untuk digandingkan.
- **Keseragaman Penskalaan Rentas Mod Paparan (Touch Slider vs 3D Flipbook) & Pengehadan Ruang Selamat**:
  Apabila menyediakan pelbagai mod paparan (seperti 3D Flipbook, Touch Slider, dan Skrol Menegak), jangan sesekali membiarkan mod selain flipbook menggunakan kelas saiz CSS mentah yang longgar seperti `max-w-[90vw]` atau `max-h-[calc(100vh-170px)]`. Pada skrin komputer riba atau semasa panel DevTools dibuka, kelas peratusan viewport ini akan mengembang secara agresif sehingga memenuhi 90% skrin, menyebabkan dokumen terasa "terlalu zoom" berbanding 3D Flipbook yang bersahaja, malah bahagian bawah dokumen melimpah ke bawah dan tertindih di sebalik toolbar navigasi terapung (`bottom-4`).
  Prinsip seni bina penskalaan konsisten rentas pemapar:
  (1) **Kongsi Formula Studio Dinamik yang Sama**: Dalam `SliderView`, gunakan pengiraan `containerDimensions` (`ResizeObserver`) yang identikal dengan `flipbook-view.tsx`: hadkan ketinggian dokumen landskap kepada maksimum 560px (dan potret 700px), serta tolak kelegaan bawah 108px (desktop) dan 88px (mudah alih) daripada ketinggian kontena supaya bar navigasi tidak sesekali bertindih dengan teks dokumen;
  (2) **Kawalan Lebar Skrol Menegak**: Dalam `VerticalView`, gunakan had kelebaran anjal `max-w-[min(90vw,780px)]` bagi landskap dan `max-w-[min(88vw,540px)]` bagi potret, serta sediakan `pb-28 sm:pb-32` pada kontena skrol supaya helaian terakhir boleh dibaca sepenuhnya dengan kelegaan selesa di atas toolbar bawah;
  (3) **Membezakan Amaran Dev Pelayan dengan Ralat Sistem**: Amaran prapemuatan pelayar (`The resource ... was preloaded using link preload but not used within a few seconds`) dan log instrumentasi Next.js (`Slow execution detected...`) di konsol DevTools pada `localhost:3000` adalah mesej diagnostik dalaman mod pembangunan Next.js/HMR, bukan ralat sistem yang merosakkan aplikasi (0 ralat sebenar).

- **Piawaian Bahasa Global (Malay to English Standardization) & Ketepatan Regex Spreadsheet**:

Namun, jangan sesekali membuang kata kunci Melayu daripada regex pemetaan kolum fail luaran (seperti `date: findHeader(['date', 'tarikh', 'tarikh acara'])` atau `isIcHeader` yang menyemak `No. Kad Pengenalan`). - **Minimalist UI & Strict Emoji Elimination Policy**:
  Elakkan penggunaan emoji berwarna-warni mentah (seperti 💻, 📱, 🎉, ⚠️, 🚫, 🔒, ⛔, 📌, ⏳, ❤️, 💬) di dalam label butang, lencana (*badges*), pill status, kad ralat, dan teks antaramuka. Penggunaan emoji mencacatkan estetika reka bentuk minimalis, kelihatan tidak profesional, dan dipaparkan secara tidak konsisten merentas pelbagai sistem operasi (Windows, macOS, iOS, Android).

  (2) **Lencana & Pill Bersih**: Pada penunjuk status (seperti orientasi dokumen), gunakan teks tipografi tulen yang kemas (contohnya `Landscape (Horizontal)` / `Portrait (Vertical)`) tanpa sebarang emoji pendahulu;
  (3) **Kad Notis & Ralat Berstruktur**: Gunakan kontena ikon bulat lembut (`w-12 h-12 rounded-full bg-rose-50 text-rose-600`) bersama ikon Lucide berpusat untuk paparan mesej yang anggun, moden, dan berwibawa.

- **Mobile Viewport Simulators & Document Orientation Adaptation**:
  Apabila membina pemapar dokumen interaktif (seperti e-pamphlet / buku program digital) yang menyokong pratonton simulator telefon di dalam pelayar desktop:
  (1) **Media Query CSS vs Bingkai Simulator**: Kelas CSS seperti `sm:inline` atau `lg:hidden` dinilai berasaskan saiz tetingkap pelayar (browser viewport), BUKAN saiz bingkai simulator anak. Apabila simulator telefon (~390px) dipaparkan pada skrin desktop (> 1024px), kelas desktop akan aktif melainkan ditentukur oleh prop JS eksplisit (`forceMobile`). Sentiasa gunakan `const isMobileLayout = forceMobile || !isDesktop;` untuk menyembunyikan elemen desktop seperti teks label butang, pemilih tema, dan kawalan stepper;
  (2) **Ergonomik Bar Navigasi Telefon (*Thumb-Zone Pill*)**: Pada peranti mudah alih, gantikan toolbar desktop yang lebar dan padat dengan *floating pill* berpusat yang padat (`[ < ]   [ ⊞ 1 / 2 ]   [ > ]` dengan `rounded-full`). Kawalan pembesar (`- 100% +`) dan penukar susun atur (`1 Page`) tidak diperlukan pada telefon kerana pengguna menggunakan sentuhan skrin (*pinch-to-zoom*, *double-tap*, dan *swipe*);
  (3) **Peluasan Tepi-ke-Tepi Dokumen Landskap**: Nisbah aspek dokumen landskap A4 (1.414 : 1) pada skrin telefon menegak (9 : 16) menghasilkan ketinggian yang terhad. Berikan kelebaran maksimum (`containerDimensions.width - 8`) supaya teks flyer dibesarkan semaksimum mungkin untuk kejelasan bacaan;
  (4) **Pengimbangan Ruang Kosong dengan Petunjuk Minimalis**: Ruang terbuka di bawah dokumen landskap yang berpusat menegak tidak wajar dibiarkan kosong tanpa konteks. Letakkan petunjuk interaksi monokromatik yang halus (`<Smartphone className="h-3.5 w-3.5 rotate-90" /> Rotate phone for full-width • Double-tap to zoom`) di bawah dokumen untuk memberikan keseimbangan visual yang disengajakan dan berprofesional.

- **Perbezaan Seni Bina Selakan 3D: Mod 2 Halaman (Dwi-Muka Surat) vs Mod 1 Halaman (Helaian Tunggal)**:
  Apabila pengguna menyatakan "2 pages okay 3d flip, 1 page je yg problem", fahami punca geometri di sebalik perbezaan kedua-dua mod ini:
  (1) **Kenapa Mod 2 Halaman Berfungsi Sempurna**: Dalam mod 2 halaman (*two-page spread*), pentas buku mempunyai dua bahagian: halaman kiri ($[0, 50\%]$) dan halaman kanan ($[50\%, 100\%]$) dengan tulang buku di tengah ($50\%$). Helaian berputar ($50\%$ lebar) berputar 180° merentasi tulang tengah dan mendarat rapi di atas halaman kiri. Seluruh pergerakan kekal berada di dalam sempadan bingkai buku 2 muka surat.
  (2) **Punca Masalah Pada Mod 1 Halaman**: Dalam mod 1 halaman (*single page / mobile*), lebar dokumen adalah $100\%$ lebar kontena. Jika helaian diputarkan 160° - 180° berpaksi pada engsel kiri (`transformOrigin: 'left center'`), helaian berputar KELUAR daripada bingkai dokumen ke ruang kosong di sebelah kiri (malah terkeluar daripada skrin telefon ke kawasan gelap). Ini kelihatan pelik dan rosak kerana tiada halaman kiri untuk helaian tersebut mendarat.
  (3) **Penyelesaian Muktamad Mod 1 Halaman (3D Paper Curl & Peel)**: Mod helaian tunggal mesti menggunakan simulasi kelengkungan kertas 3D sejati (*authentic 3D paper curl & peel* seperti Apple Books / StPageFlip) yang kekal terkandung di dalam kontena (`overflow-hidden`):
      - Bucu helaian terangkat dalam perspektif 3D dengan putaran `rotateY: -25deg` dan kecondongan pepenjuru organik `rotateZ: -3deg` berpaksi pada `right center`.
      - Jalur bayangan kertas 3D tebal dwi-lapisan (`shadow-[-16px_0_36px_rgba(0,0,0,0.32),-6px_0_12px_rgba(0,0,0,0.2)]`) mengekori lipatan selakan dan jatuh ke atas muka surat baharu di bawah.
      - Kilauan silinder 3D (*cylindrical highlight sheen* `from-white/60 via-black/10 to-transparent`) membiaskan cahaya di sepanjang permatang lengkungan kertas.
      - Helaian menyapu licin dari kanan ke kiri (`x: 0 -> -102%`) dan bergulung kemas ke dalam tulang kiri, menyingkap halaman baharu di bawahnya tanpa sebarang pembengkakan kamera, tanpa terpelanting keluar skrin, dan sifar garisan tengah.

- **Penghapusan Glitch Visual Selepas Animasi 3D Flip (Seamless Frame-Perfect Handoff & Shadow Dissolve)**:
  Apabila pengguna melaporkan "bila lepas 3d flip tu rasa macam ada glitch sikit", ini berpunca daripada 5 isu serentak sewaktu helaian selakan dinyah-lekap (*unmounted*):
  (1) **Lonjakan Transformasi `targetShiftX`**: Menetapkan `targetSpreadRef.current = null` secara segerak di dalam `onFlipAnimationComplete` menyebabkan `targetShiftX` membaca `activeSpread` (spread lama) sebelum render baharu berlaku, mencetuskan lonjakan sekejap pada koordinat paksi X kontena. Gunakan `requestAnimationFrame` untuk memastikan rujukan spread sasaran kekal aktif sehingga render keadaan baharu telah selamat dikomit;
  (2) **Pertukaran Mendadak `img.src` Halaman Tapak (*Decode Flash*)**: Apabila helaian selakan dinyah-lekap serentak dengan arahan menukar `src` pada elemen `<img>` halaman tapak di bawahnya, pelayar memerlukan 1 frame untuk mendekod bitmap baharu, menyebabkan kelipan kosong/putih seketika. Selesaikan dengan memasang imej sasaran terlebih dahulu secara tersembunyi (*pre-mounted target image*) di dalam kontena tapak dari detik awal selakan (t=0), dan tangguhkan nyah-lekap helaian selakan sebanyak 1 frame menerusi `requestAnimationFrame` agar halaman tapak telah sedia terpapar sepenuhnya sebelum helaian diangkat;
  (3) **Penyelarasan Bayangan Helaian (*Drop-Shadow Dissolve*)**: Jangan biarkan bayangan jatuh (`drop-shadow-xl`) kekal pada intensiti penuh apabila helaian mendarat rata pada 180° / 0°. Animasikan penapis bayangan `filter: ['drop-shadow(0px 0px 0px rgba(0,0,0,0))', 'drop-shadow(±8px 12px 24px rgba(0,0,0,0.32))', 'drop-shadow(0px 0px 0px rgba(0,0,0,0))']` dengan `times: [0, 0.48, 1]` supaya bayangan kembali ke 0 sebelum helaian dinyah-lekap;
  (4) **Penyelarasan Kelegapan Sempadan (*Border Opacity Consistency*)**: Pastikan warna sempadan pada kedua-dua permukaan helaian selakan sepadan 100% dengan sempadan halaman tapak (`border-black/15`, bukan `border-black/10`), menghapuskan lompatan warna garis luar pada saat akhir;
  (5) **Pembetulan Selakan Undur Mod 1 Halaman (*Single Page PREV Flip*)**: Pada mod 1 muka surat, selakan ke belakang memerlukan bayangan hala kanan (`shadow-[16px_...], bukan shadow-[-16px_...]`), prapemuatan imej halaman sasaran di lapisan tapak, serta pudar masuk kelegapan (`opacity: [0, 1, 1]`) bagi menghapuskan kelipan halaman lama sewaktu mendarat.

- **Penyelarasan Segerak Transisi Imej dengan Putaran 3D Flipbook (Symmetrical Midpoint Apex & Pure Peel Architecture)**:
  Apabila pengguna melaporkan "dari segi 3d flip macam okay utk 1 page dan 2 pages, cuma utk trasition gambar tu macam tak sync bila 3d flip", ini berlaku disebabkan 4 punca dinamik pergerakan imej vs putaran fizikal:
  (1) **Ketidakseimbangan Lengkungan Easing (*Easing Curve Front-Loading*)**: Penggunaan lengkungan ease-out mendadak seperti `cubic-bezier(0.25, 1, 0.5, 1)` menyebabkan putaran melepasi sudut 90° dalam ~75ms pertama daripada tempoh 520ms animasi (iaitu hanya pada 15% masa). Akibatnya, imej muka hadapan hilang serta-merta pada permulaan selakan dan bertukar kepada imej belakang, manakala helaian itu sendiri mengambil baki 445ms untuk perlahan-lahan mendarat. Pengguna melihat ini sebagai pertukaran imej yang "terlalu awal / tak sync dengan pusingan". Penyelesaian: Gunakan lengkungan masa simetri `cubic-bezier(0.45, 0.05, 0.55, 0.95)` di mana titik putaran 90° (apex berserenjang) dicapai tepat pada 50% masa selakan (260ms). Muka hadapan dan muka belakang masing-masing kelihatan selama 260ms, menyelaraskan pertukaran imej tepat di puncak pusingan 3D;
  (2) **Pemisahan Kedalaman Mikro (*translateZ(1px) anti-Z-Fighting*)**: Pada satah 3D dwi-muka surat di mana muka hadapan (`rotateY: 0deg`) dan muka belakang (`rotateY: 180deg`) berkongsi kedalaman $Z = 0$, enjin rasterisasi WebKit/Blink mengalami *Z-fighting* di mana piksel muka belakang bocor sebelum waktunya. Tambahkan `translateZ(1px)` pada kedua-dua permukaan untuk memastikan peralihan visual muka surat dipotong tepat pada sudut 90°;
  (3) **Penyingkiran Tag `<img>` Bertindih Pendua di Halaman Tapak**: Menambah tag `<img>` kedua secara serentak di dalam kontena tapak bagi tujuan "pre-mount" menyebabkan fenomena bayangan berganda (*ghosting*) dan pertindihan rendering telus. Sebaliknya, gunakan prapemuatan cache di latar belakang (`new Image().src = url`) dalam `useEffect` tanpa menyentuh pohon DOM;
  (4) **Kesimetrian Mengupas Helaian Mod 1 Muka Surat (*Symmetrical Pure Peel*)**: Dalam mod 1 muka surat, selakan NEXT dan PREV mesti beroperasi mengikut prinsip yang sama:
      - NEXT: Halaman tapak bersedia dengan `nextPage`, helaian semasa mengupas ke kiri (`x: 0% -> -105%`, `rotateY: -25deg`, paksi kanan), mendedahkan `nextPage` di bawahnya.
      - PREV: Halaman tapak bersedia dengan `prevPage`, helaian semasa mengupas ke kanan (`x: 0% -> 105%`, `rotateY: 25deg`, paksi kiri), mendedahkan `prevPage` di bawahnya.
      Kedua-dua arah memaparkan muka surat destinasi pada lapisan tapak sejak $t=0$, menjadikan penyingkapan gambar 100% seiring dan segerak dengan pergerakan helaian fizikal.

- **Penyelarasan Mutlak Transisi Imej 2 Halaman (Two-Page Spread Synchronization & Pure 3D Context Integrity)**:
  Apabila pengguna menyatakan "utk 1 page dh okay, utk 2 pages ni macam tak okay sikit, bila 3d flip gambar tak berapa nk sync", fahami punca fizikal dan visual yang khusus pada susun atur dwi-halaman:
  (1) **Runtuhan Konteks 3D Akibat CSS `filter` (*Context Flattening Bug*)**: Meletakkan `filter: drop-shadow(...)` pada kontena `<motion.div>` yang mempunyai `transformStyle: 'preserve-3d'` melanggar spesifikasi W3C CSS Transforms di mana sebarang penapis CSS meratakan (*flattens*) ruang 3D menjadi satah bitmap 2D. Ini mematikan fungsi `backface-visibility: hidden` dan memecahkan susunan kedalaman Z (*depth sorting*). Penyelesaian: Jangan sesekali meletakkan `filter` pada bekas 3D berputar. Gunakan animasi `boxShadow` pada elemen muka hadapan dan belakang yang melarut licin ke 0px apabila helaian mendarat rata;
  (2) **Perangkap Lengkungan Easing Terlalu Curam**: Lengkungan seperti `[0.45, 0.05, 0.55, 0.95]` mempunyai nisbah cerun $\Delta y / \Delta x = 0.90 / 0.10 = 9.0$ di tengah animasi. Ini memecutkan putaran daripada 9° ke 171° dalam hanya 50ms, menyebabkan imej kelihatan seperti menyentap mendadak dan tidak selari dengan selakan tangan manusia. Gantikan dengan lengkungan fizik klasik yang anggun `cubic-bezier(0.42, 0, 0.58, 1)` dengan tempoh 540ms dan selaraskan peralihan CSS anjakan kontena (`transform 540ms cubic-bezier(0.42, 0, 0.58, 1)`) agar kedua-duanya bergerak seirama;
  (3) **Prapemuatan Menyeluruh Mengikut Unit Spread (*Spread-Aware Preloading*)**: Dalam mod 2 halaman, setiap kali selakan berlaku, pergerakan melangkau 2 muka surat. Prapemuatan ringkas `currentPage ± 2` gagal memuat turun muka surat kedua spread berikutnya (`currentPage + 3`). Prapemuat kesemua halaman bagi risalah bersaiz sederhana ($\le 16$ halaman) atau $\pm 5$ halaman ke hadapan/belakang bagi risalah besar agar imej sentiasa 100% berada dalam memori pelayar sebelum butang ditekan;
  (4) **Pembalikan Geometri Muka Belakang (*Back Face Geometric Inversion*)**: Apabila muka belakang diputarkan 180° dan mendarat di sebelah kiri (selakan NEXT), bucu luar berada di sisi kiri (`rounded-l-2xl border-l`) dan bayangan lipatan tulang buku berada di sisi kanan (`right-0 bg-gradient-to-l`). Sebaliknya pada selakan PREV, bucu luar berada di sisi kanan (`rounded-r-2xl border-r`) dan bayangan tulang di sisi kiri (`left-0 bg-gradient-to-r`);
  (5) **Kawalan Nullish Halaman Tapak Semasa Menutup Buku**: Elakkan operator fallback `targetSpreadRef.current?.leftPage ?? activeSpread.leftPage` kerana semasa menutup buku ke kulit hadapan, `leftPage` sengaja bernilai `null`. Fallback yang salah akan memaparkan halaman lama di atas meja sewaktu helaian diangkat, mencetuskan fenomena helaian pendua (*duplicate page flash*). Gunakan `isLeftBaseHidden` dan `isRightBaseHidden` untuk menyembunyikan halaman tapak dengan bersih.

- **Penjanaan ID Kanvas Bebas Kolisi, Komit Kelompok Atomik, dan Geometri Adaptif Preset**:
  Apabila pengguna melaporkan ralat konsol React `Encountered two children with the same key, el-...` semasa menggunakan preset kanvas (seperti *Dual Signature Preset* atau *Classic Border*):
  (1) **Kegagalan `Date.now()` Dalam Gelung Segerak**: `Date.now()` mengembalikan nombor milisaat Unix. Jika operasi mencipta beberapa elemen berturut-turut dalam fungsi yang sama (contohnya 4 panggilan `addElement` serentak), kesemua elemen dicipta dalam milisaat yang sama dan menerima ID pendua yang identikal. Kunci pendua ini merosakkan rekonsiliasi DOM maya React, menyebabkan tingkah laku pemilihan, penyeretan (*drag*), dan pemadaman elemen menjadi rosak dan tidak menentu.
  (2) **Penjana ID Unik Teguh (`generateElementId`)**: Jangan sesekali bergantung pada `Date.now()` semata-mata. Bina penjana ID yang menggabungkan:
      - Awalan jenis elemen (`el`, `text`, `shape`),
      - Timestamp semasa (`Date.now()`),
      - Rolling counter sesi atomik tempatan (`(counter + 1) % 1000000`),
      - Entropi rawak kriptografik/Base-36 (`Math.random().toString(36).substring(2, 8)`).
      Formula `${prefix}-${Date.now()}-${counter}-${rand}` menjamin sifar kolisi walaupun 10,000+ elemen dijana dalam milisaat yang sama.
  (3) **Kemas Kini Kelompok Atomik (`addElements`)**: Preset yang menambah pelbagai elemen tidak wajar memanggil `addElement` berulang kali kerana setiap panggilan mencetuskan kemas kini state `setTemplate` dan sejarah undo `commitToHistory` berasingan. Sediakan kaedah `addElements(array)` yang menambah kesemua elemen ke dalam kanvas serentak dalam satu transaksi state dan satu sejarah komit, membolehkan pengguna membatalkan (`Ctrl+Z`) keseluruhan preset dengan 1 langkah undo.
  (4) **Geometri Adaptif Orientasi (Landscape vs Portrait)**: Jangan gunakan koordinat piksel statik (seperti `x: 853`) yang melebihi lebar kanvas potret (794px). Kira kedudukan secara berkadar berdasarkan lebar (`w`) dan tinggi (`h`) kanvas (`w * 0.28` dan `w * 0.72` untuk potret; `w * 0.25` dan `w * 0.75` untuk landskap) dengan garisan di `h - 180px` agar elemen sentiasa berada di dalam kanvas dan simetri.
  (5) **Sanitasi Kunci Legasi Klien (*Self-Healing On Mount*)**: Untuk templat sedia ada yang telah disimpan dengan ID pendua dalam pangkalan data sebelum pembaikan, gunakan sanitasi `useMemo` semasa memuatkan templat pada komponen induk (`sanitizedInitialTemplate`) untuk mengesan dan menggantikan ID pendua dengan ID unik baharu secara automatik sebelum dihantar ke kanvas dan sejarah undo.

- **Spesifikasi Ketat HTML5 `<input type="color">` & Penghapusan Amaran "The specified value does not conform to the required format"**:
  Apabila konsol pelayar merekodkan amaran:
  `The specified value "transparent" does not conform to the required format. The value must be a valid CSS color.`
  (1) **Spesifikasi W3C HTML5 Color Input**: Elemen `<input type="color">` natif pelayar HANYA sah menerima rentetan 7-aksara format heksadesimal huruf kecil `#rrggbb` (cth. `#ffffff` atau `#000000`). Menyalurkan nilai seperti `"transparent"`, `"none"`, `"rgb(...)"`, `""`, atau `null` akan ditolak oleh enjin DOM pelayar (Chromium/WebKit/Firefox), lalu pelayar menetapkan nilai fallback `#000000` secara senyap dan mencetak amaran ke konsol pada setiap kitaran render;
  (2) **Punca Lazim dalam Canvas Builder**: Preset reka bentuk (seperti sempadan sijil atau garisan) sering kali menetapkan `fill: 'transparent'`. Di dalam panel sifat elemen, ungkapan seperti `value={selectedElement.fill || '#e5e7eb'}` menilai kepada `'transparent'` kerana `'transparent'` adalah rentetan bukan kosong (*truthy*). Akibatnya, pada setiap acara pergerakan tetikus, seretan (*drag*), atau taipan teks, komponen yang me-render semula akan menolak `"transparent"` ke input warna puluhan kali (cth. 38 kali berturut-turut);
  (3) **Fungsi Sanitasi Sejagat (`toValidHexColor`)**: Sentiasa lindungi nilai prop `value` bagi mana-mana `<input type="color">` menggunakan fungsi penapis:
      ```ts
      export function toValidHexColor(color: string | undefined | null, fallback = '#000000'): string {
        if (!color || typeof color !== 'string') return fallback;
        const trimmed = color.trim().toLowerCase();
        if (['transparent', 'none', 'inherit', 'initial', 'unset'].includes(trimmed)) return fallback;
        if (/^#[0-9a-f]{6}$/.test(trimmed)) return trimmed;
        if (/^#[0-9a-f]{3}$/.test(trimmed)) return `#${trimmed[1]}${trimmed[1]}${trimmed[2]}${trimmed[2]}${trimmed[3]}${trimmed[3]}`;
        if (/^#[0-9a-f]{8}$/.test(trimmed)) return trimmed.substring(0, 7);
        if (/^[0-9a-f]{6}$/.test(trimmed)) return `#${trimmed}`;
        if (/^[0-9a-f]{3}$/.test(trimmed)) return `#${trimmed[0]}${trimmed[0]}${trimmed[1]}${trimmed[1]}${trimmed[2]}${trimmed[2]}`;
        return fallback;
      }
      ```
  (4) **Pengasingan UI Isian Lutsinar vs Warna Sempadan**: Untuk bentuk geometri (segi empat / bulatan), sediakan kotak semak khusus `No Fill (Transparent)`. Apabila diaktifkan, sembunyikan atau nyahaktifkan pemilih warna isian, dan sediakan pemilih warna sempadan (`stroke`) serta ketebalan sempadan (`strokeWidth`) supaya pengguna mempunyai kawalan reka bentuk penuh tanpa memicu ralat pelayar.

- **Penghapusan Ralat Hidrasi Radix `DialogTrigger` / `AlertDialogTrigger` Dalam Server Component (`aria-controls` Hydration Mismatch)**:
  Apabila konsol pelayar merekodkan ralat:

  dengan perbezaan pokok DOM pada:
  `<DialogTrigger asChild> -> <button aria-controls="radix-_R_...">`
  (1) **Punca Perbezaan Id `useId()` Antara SSR dan Hidrasi Klien**:
      Komponen Radix UI (`@radix-ui/react-dialog`, `@radix-ui/react-alert-dialog`) menjana ID kontena kandungan secara dinamik menggunakan `useId()` bagi memenuhi keperluan aksesibiliti ARIA (`aria-controls`, `aria-describedby`).       );

  (2) **Penyelesaian Muktamad: Gunakan `mode="popLayout"`**:

      const [[page, direction], setPageAndDirection] = useState([currentPage, 0]);

- **Ketinggian Viewport Mudah Alih & Pemotongan Elemen Bawah (`min-h-[100dvh]` vs `min-h-screen` / `100vh`)**:
  (1) **Punca Masalah (The Mobile Viewport Bug)**:
      Dalam CSS, `min-h-screen` atau `min-height: 100vh` ditafsirkan oleh pelayar mudah alih (Google Chrome, Safari di Android & iOS) sebagai *Large Viewport Height* (LVH) — iaitu anggaran ketinggian skrin apabila palang alamat URL (*address bar*) dan bar navigasi pelayar disembunyikan / ditarik ke atas. Namun, semasa pengguna mula membuka halaman web (keadaan lalai / default), palang URL dan bar navigasi pelayar berada dalam keadaan terbuka sepenuhnya (*expanded*). Ini menjadikan ruang pandang sebenar (*visible viewport*) sekitar 56px hingga 80px lebih kecil daripada `100vh`.
  (2) **Kesan Terhadap Susun Atur `justify-between`**:
      Apabila bekas utama menggunakan `min-h-screen flex flex-col justify-between`, enjin pelayar memanjangkan bekas ke `100vh`. Footer atau lencana jenama (cth: *"Create your own with KlikForm"*) ditolak ke paras dasar bekas `100vh` yang terletak 56px di luar bahagian bawah skrin telefon. Akibatnya, separuh daripada lencana terpotong di birai bawah skrin, dan pengguna terpaksa menatal ke bawah (*scroll down*) semata-mata untuk melihat lencana penuh walaupun halaman hanya mempunyai beberapa baris pautan ringkas yang sepatutnya muat dalam satu skrin penuh tanpa sebarang tatalan.
  (3) **Penyelesaian Kejuruteraan**:
      - Sentiasa sertakan `min-h-[100dvh]` bersama `min-h-screen`: `className="min-h-screen min-h-[100dvh] flex flex-col justify-between ..."` supaya pada pelayar mudah alih moden, ketinggian minimum terikat tepat kepada *Dynamic/Small Viewport Height* (`100dvh`/`100svh`) semasa palang URL terbuka. Profil ringkas akan muat 100% pada skrin tanpa sebarang skrol atau penolakan elemen ke luar skrin.
      - Gunakan formula ruang selamat dinamik untuk padding bawah: `pb-[max(1.5rem,env(safe-area-inset-bottom))]` bagi menjamin jarak pernafasan sekurang-kurangnya 24px di atas bar navigasi 3-butang Android (`≡ ☐ ◁`) mahupun bar sentuh iOS (*home indicator bar*).
      - Berikan `shrink-0` pada elemen `<footer>` supaya lencana penjenamaan tidak dimampatkan atau dipenyek oleh enjin flexbox semasa kandungan halaman bertambah.
