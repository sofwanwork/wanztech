# Development Lessons

- **Full-Bleed Children in Shadcn `Card` & Ghost Margins (`py-6 gap-6`)**: In shadcn/ui components (`components/ui/card.tsx`), `Card` defaults to `flex flex-col gap-6 py-6`. When nesting subcomponents with full-bleed backgrounds (such as a header toolbar `<CardHeader className="bg-white border-b">`, an interactive workbench canvas `<CardContent className="p-0 bg-slate-100">`, or a footer strip `<CardFooter className="bg-slate-50 border-t">`), omitting an explicit padding/gap reset on the parent `<Card>` leaves the 24px vertical padding (`py-6`) and 24px children gap (`gap-6`) active. This creates glaring white bands / gaps ("lopong putih") above, below, and between adjacent colored sections.
  1. *Complete Elimination*: Always override the card wrapper with `<Card className="p-0 gap-0 overflow-hidden ...">`. `p-0` removes top and bottom padding, `gap-0` eliminates inter-child spacing, and `overflow-hidden` clips children seamlessly to the card's `rounded-xl` or `rounded-2xl` corners without border leakage.
  2. *Studio Workbench Realism*: Rather than using flat gray backdrops (`bg-gray-200`) which look like unstyled wireframes, use a subtle studio workbench matrix (`radial-gradient(rgba(148, 163, 184, 0.4) 1px, transparent 1px) [background-size:20px_20px]`) paired with realistic ambient paper drop shadows (`shadow-[0_20px_50px_rgba(0,0,0,0.16),0_4px_16px_rgba(0,0,0,0.08)]`) and a micro border ring (`ring-1 ring-black/10`).
  3. *Zoom Pan & Centering Geometry*: Use `m-auto` on the child frame inside scrollable flex containers (`overflow-auto`) so that when the certificate is zoomed out it centers perfectly, and when zoomed in ($> 100\%$) it scrolls smoothly across both axes without negative coordinate clipping ($X < 0$ or $Y < 0$).
  4. *Human-Friendly Date Formatting*: Spreadsheet and database responses often return raw ISO timestamp strings (e.g. `2026-10-07T02:05:47.358Z`). Always format them through `toLocaleDateString` into clean, human-readable dates (`October 7, 2026`) on user-facing verification cards.
  5. *Shadcn `Button variant="outline"` Light Background Trap*: In shadcn/ui `button.tsx`, `variant: outline` explicitly injects `bg-background` (which resolves to white `#ffffff` in light mode). If placed inside a dark container (such as a dark modal header/footer `bg-slate-900`) and styled with `text-slate-200` under the assumption that the button has a transparent background, the button renders as an opaque white rectangle with nearly-white text (`#e2e8f0` on `#ffffff`), rendering the label completely invisible ("tulisan tak nampak"). On dark surfaces, never use `variant="outline"` with light text; either use an explicit white button with dark text (`bg-white text-slate-900 font-semibold`) or use `variant="ghost"` with a dark background (`bg-slate-800 text-slate-200 hover:text-white`).
  6. *Orphan Words & Dynamic Header Balance (`[text-wrap:balance]`)*: Dynamic event/form titles often wrap awkwardly, leaving a single dangling word or short year tag (e.g. `2026)`) alone on the second line because browser word-wrapping is greedy by default. Always apply `[text-wrap:balance]` combined with a sensible typographic constraint (`max-w-3xl sm:max-w-4xl mx-auto`) and snug line-height (`leading-snug sm:leading-tight`) on public title headings (`<h1>`). The browser then automatically distributes the text symmetrically between lines without any manual line breaks.

7. *Native Windows Scrollbar Suppression (`no-scrollbar` / `[scrollbar-width:none]`)*: On Windows Chromium browsers, scrollable containers (`overflow-auto` or `overflow-y-auto`) render thick 17px default scrollbars that look jarring inside dark studio modals, canvas workbenches, and dashboard sidebars.
  - *Modals & Canvas*: When `baseModalScale` relies on `window.innerHeight * 0.7` without accounting for modal chrome (header ~52px, footer ~52px, padding ~48px), smaller laptop viewports easily exceed `max-h-[94vh]`, triggering the scrollbar even in 'Fit' mode. To achieve a clean canvas feel: (a) Use formula `Math.min((window.innerWidth * 0.82) / captureWidth, Math.max(0.2, (window.innerHeight * 0.86 - 150) / captureHeight))` to guarantee fit without initial overflow; (b) Apply `no-scrollbar [scrollbar-width:none] [-ms-overflow-style:none] [&::-webkit-scrollbar]:hidden overscroll-contain` so mouse wheel, trackpad, and touch panning work smoothly when zoomed in without any visible scrollbar.
  - *Dashboard Sidebar Navigation*: When sidebar navigation lists exceed the viewport height on 14-inch laptops (~710px total height from logo + 9 nav items + user profile footer), `overflow-y-auto` renders an unsightly gray scrollbar right next to the menu items. Applying `no-scrollbar [scrollbar-width:none] [-ms-overflow-style:none] [&::-webkit-scrollbar]:hidden overscroll-contain` along with compact vertical spacing (`py-5 px-3 space-y-1.5` and `mb-4`) hides the scrollbar completely while maintaining full mouse wheel and touch-swipe scrollability.
8. *14-Inch Laptop Card Grids & Text Badges (`whitespace-nowrap shrink-0`)*: On 14-inch laptops (1280px - 1440px width), standard Tailwind breakpoints like `xl:grid-cols-4` create a trap: after subtracting the 256px sidebar and page padding, only ~1000px remains. Dividing 1000px across 4 columns reduces card widths to ~230px, crushing flex footers and wrapping text badges (like `Oct 2, 2026` breaking across spaces into 3 vertical lines). To prevent this: (a) Use `lg:grid-cols-3 2xl:grid-cols-4` so cards maintain a comfortable ~320px width on laptops; (b) Always add `whitespace-nowrap shrink-0` to date and status badges inside flex containers; (c) In `stripHtml`, decode HTML entities (`&nbsp;`, `&amp;`, etc.) so rich text editor outputs don't leak raw entities into card previews.
9. *Dual Scrollbar Traps in Radix/Shadcn Dialogs (`min-h-0` & `overflow-hidden`)*: In Radix/shadcn modals (`DialogContent`), omitting `overflow-hidden` causes `overflow-x-hidden` (from base styles) to compute `overflow-y` to `auto`. If child `<form>` or `<Tabs>` elements lack `min-h-0`, CSS Flexbox's default `min-height: auto` prevents children from shrinking below their content height. This expands the dialog past `max-h-[90dvh]` and triggers an OUTER scrollbar, while inner scrollable lists (like `TabsContent overflow-y-auto`) trigger an INNER scrollbar — creating two ugly native Windows scrollbars side by side. Fix: (1) Set `overflow-hidden no-scrollbar` on `DialogContent`; (2) Add `min-h-0` to all intermediate flex parents (`form`, `Tabs`); (3) Equip scrollable `TabsContent` with `no-scrollbar [scrollbar-width:none] [-ms-overflow-style:none] [&::-webkit-scrollbar]:hidden overscroll-contain`.
10. *Rich Text ProseMirror Description Mobile Jumble & Paragraph Margins (`[&>p]:mb-0` Trap)*: When rendering rich-text HTML (e.g. from TipTap / ProseMirror) inside public forms (`app/(public)/form/[id]/client.tsx`), setting `[&>p]:mb-0` to eliminate default browser paragraph gaps creates a severe visual breakdown on mobile devices. On desktop, metadata entries (such as `Tarikh : ...`, `Masa : ...`, `Tempat : ...`) fit on a single line, making `mb-0` look like a compact metadata list. However, on narrow mobile screens (~320px - 360px), long lines inevitably wrap. Because `mb-0` strips all paragraph bottom margins, wrapped lines wrap all the way flush left to column 0 under the labels, appearing identical in spacing to the next paragraph. This turns the entire description into an unintelligible, jagged wall of text where orphan words and separate items blur together.
  - *Fix*: (a) Replace `[&>p]:mb-0` with `[&>p:not(:last-child)]:mb-2.5 sm:[&>p:not(:last-child)]:mb-2`, restoring a clean 10px visual separation between distinct paragraphs; (b) Handle blank spacer lines with `[&>p:empty]:h-2 [&>p:empty]:mb-0`; (c) Apply `text-sm sm:text-base leading-relaxed text-slate-600` so mobile screens fit more characters naturally with comfortable reading height; (d) High-contrast bold tags (`[&_strong]:font-bold [&_strong]:text-slate-900 [&_b]:font-bold [&_b]:text-slate-900`) so labels pop immediately against body text.
11. *ASCII Scale Diagrams in Separators & Rating Overflow (`w-20` Ghost Margin Trap)*: Form creators frequently copy-paste or type ASCII scale diagrams (e.g. `1----------------------> 6 Sangat tidak setuju          Sangat Setuju`) into section separator descriptions to guide respondents on rating questions.
  - *Separator Scale Breakdown*: Long runs of 40+ raw hyphens/dashes overflow narrow mobile containers (~320px) and wrap mid-arrow, splintering the scale diagram into 3 jagged, disconnected lines. Solution: Detect the pattern via `parseScaleGuide` (`lib/forms/scale-guide.ts`) and render an adaptive visual scale card `( 1 ) ────────► ( 6 )` with pill badges, fluid connector line, and min/max labels below that flex gracefully to any screen width.
  - *Rating Cutoff & Grey Scrollbar*: Static side containers `<div className="w-20">` (160px combined) were rendered even when `minLabel` and `maxLabel` were undefined. In a 272px mobile card, this left only 112px for 6 rating buttons, clipping circle 6 and spawning an unsightly native horizontal scrollbar. Solution: Move min/max labels underneath the scale row (industry standard in Google Forms / Typeform), allocate 100% card width to the scale buttons with `justify-between sm:justify-center`, and suppress native scrollbars via `no-scrollbar [scrollbar-width:none]`.
12. *Mobile Viewport Horizontal Scroll Lockdown & Short-Form Vertical Optimization (`100dvh` & Shadcn Ghost Margin)*:
  - *Horizontal Scroll Wiggle*: On mobile browsers, omitting `overflow-x: hidden; max-width: 100vw;` on `html, body` allows any subpixel rounding, outer box shadow blur (`shadow-lg`), or fixed elements with `w-full` (which computes to `100vw`, including scrollbar width) to trigger rubber-band horizontal scrolling. In addition, `backgroundAttachment: 'fixed'` causes severe WebKit/Chrome Android viewport expansion bugs. Solution: (a) Add `max-width: 100vw; overflow-x: hidden;` to `html, body` in `@layer base`; (b) Use `fixed top-0 inset-x-0` instead of `w-full`; (c) Omit `backgroundAttachment: 'fixed'`; (d) Explicitly export `viewport: Viewport = { width: 'device-width', initialScale: 1 }` in `app/layout.tsx`.
  - *Short-Form Vertical Height*: Standard shadcn `<Card>` applies `py-6 gap-6` (48px padding + 24px gap). When rendering dynamic forms, omitting `p-0 gap-0 overflow-hidden` creates 72px of ghost whitespace. Compounded by `min-h-screen` (which resolves to `100vh` ignoring mobile browser address bars), `py-8` outer padding, `space-y-6`, and large `mt-8` footers, a simple 4-question form blew up to ~894px height, forcing mobile respondents to scroll vertically on empty space. Solution: (a) Use `min-h-screen min-h-[100dvh] py-3 sm:py-8 md:py-12 px-3 sm:px-4`; (b) Lock the fields card with `p-0 gap-0 overflow-hidden rounded-2xl sm:rounded-3xl shadow-sm border border-gray-200/80`; (c) Compact field row padding to `py-3.5 sm:py-5 px-4 sm:px-6` and `CardFooter` to `p-4 sm:p-6 gap-3 sm:gap-4`; (d) Compact Powered by to `mt-4 sm:mt-8 pb-4 sm:pb-8`. Saves ~260px, allowing short forms to fit cleanly on 1 screen without scrolling.
13. *Multiple Choice Grid (Scale / Matrix) Architecture & Mobile Adaptive Stacks*:
  - *Google Sheets Column Flattening*: Storing matrix responses as opaque JSON strings (`{"row1":"5"}`) forces spreadsheet users to write complex parsing formulas. Instead, `flattenGridResponses` emits flattened key-value pairs formatted as `formatGridRowKey(field.label, row)` (e.g. `Penilaian Kursus [Penceramah Jelas] = 5`). In tandem with `sheet.setHeaderRow([...headers, ...missingHeaders])`, Google Sheets automatically generates distinct columns for every statement on submission, mirroring Google Forms.
  - *Mobile Viewport Elimination of Horizontal Overflow*: Traditional desktop tables (`<table>`) forced onto mobile screens inevitably overflow horizontally ($> 450px$), re-triggering horizontal scroll bounce. Using a dual-layout strategy: render a symmetric matrix `<table>` on desktop (`hidden md:block`), and an *Adaptive Mobile Stack* (`block md:hidden`) where each row statement is a dedicated sub-card with thumb-friendly touch buttons ($40px$ height `h-10`, `w-full`, $0$ horizontal overflow, dynamic row counter badge `X / Y dijawab`).
  - *Edit Mode Snapshot Reconstitution*: When loading snapshots from Google Sheets / database in `/edit/[token]`, `unflattenGridResponses(field, snapshot)` walks `field.gridConfig.rows` to reconstruct the dictionary `{ [row]: columnValue }` into `initialValues[field.id]`, allowing respondents to edit pre-filled grid responses effortlessly.
14. *Google Sheets Date Override Precedence over Automated Check-In Records*:
  - *Root Cause of Stale Dates*: When building daily certificate options (`buildDailyCertificateOptions`), seeding the options map from automated Supabase DB check-in records (`records`) and guarding subsequent Google Sheet column processing with `if (!optionsMap.has(dayNum))` causes any user-edited or backdated dates in Google Sheets to be completely ignored. Because the participant originally checked in using the QR code, `optionsMap.has(dayNum)` was already true, locking the option to the raw database timestamp forever.
  - *Priority-Based Precedence Architecture*: The connected Google Sheet is the organizer's active control center. When an organizer edits attendance or dates in the sheet, their spreadsheet values MUST take precedence over automated check-in timestamps. Implement a priority hierarchy via `priorityMap`:
    1. Explicit Date column (`Tarikh (Hari X)`, `Date (Day X)`, `Tarikh Hari X`) -> Priority 30 (Highest).
    2. Check-In column (`Masa Masuk (Hari X)`, `Check In (Hari X)`) -> Priority 20.
    3. Check-Out column (`Masa Keluar (Hari X)`, `Check Out (Hari X)`) -> Priority 10.
    4. Generic Day label (`Hari X`, `Day X`) -> Priority 5.
    5. Automated DB Record (`attendance_records.check_in_at`) -> Priority 0 (Baseline fallback).
  - *Malaysian Date Parsing & Time Stripping*: Spreadsheet cells frequently contain formatted strings like `"18/10/2026, 04:15 PM"`, `"18-10-2026"`, `"18.10.2026"`, or Malay month names (`"18 Oktober 2026"`, `"18hb Oktober 2026"`). Stripping trailing time before parsing, matching DD/MM/YYYY, and normalizing Malay month names to English prevents JavaScript's V8 `new Date()` from returning `Invalid Date`, ensuring clean date rendering on certificates. Multi-day range strings (e.g. `"7 & 8 Oktober 2026"`) are safely preserved.
15. *Dedicated Daily Google Sheet Worksheets for Multi-Day Attendance (`syncDailyAttendanceToSheet`)*:
  - *Column Proliferation on Sheet 0*: In multi-day check-in/check-out events (`totalDays > 1`), appending columns for every subsequent day (`Masa Masuk (Hari 2)`, `Masa Keluar (Hari 2)`, `Masa Masuk (Hari 3)`, etc.) makes Sheet 0 excessively wide and difficult for organizers to review on smaller screens.
  - *Segregated Daily Worksheets Architecture*: Keep Day 1 attendance and initial form registration submissions cleanly on Sheet 0. For Day 2 and subsequent days, dynamically query or create a dedicated daily tab via `doc.sheetsByTitle['Hari ' + dayNumber] || await doc.addSheet({ title: 'Hari ' + dayNumber, headerValues: [...] })`. Standardized daily headers (`Timestamp`, `Nama`, `No. IC`, `Masa Masuk`, `Masa Keluar`, `Jumlah Jam (Hours)`, `Status Kehadiran`) guarantee consistent, auditable day-by-day attendance tables.
  - *Dual-Update Protocol*: When a participant checks in or out on Day 2+, add or update their row in that day's dedicated tab, while simultaneously updating the cumulative summary columns (`Status Kehadiran`, `Jumlah Masa Hadir`, `Jumlah Jam Keseluruhan (Total Hours)`) on Sheet 0. Organizers enjoy a high-level master dashboard on Sheet 0 and deep day-by-day logs in separate tabs.
  - *Bidirectional Certificate Scanner & Defensive Mock Safety*: In `checkCertificateByICOrEmail` (`actions/certificates.ts`), scan Sheet 0 first, then inspect `doc.sheetsByTitle` defensively (`doc.sheetsByTitle || {}` to prevent crashes when unit test mocks only mock `sheetsByIndex`). Map daily tab rows into `sheetRowData` (`Masa Masuk (Hari ${d})`), allowing `buildDailyCertificateOptions` to inherit custom date edits seamlessly with 100% backward compatibility for legacy single-sheet events.
16. *Form Label `<label for=FORM_ELEMENT>` Mismatches in Composite Question Groups*:
  - *Root Cause of Chrome DevTools Warning*: The HTML specification (WHATWG) and WCAG 1.3.1 / 4.1.2 require that a `<label for="...">` MUST reference the ID of an existing labelable form control (`<input>`, `<textarea>`, `<select>`, `<button>`). Emitting `<Label htmlFor={`field-input-${field.id}`}>` unconditionally at the top of all question types causes Chrome DevTools to flag `Incorrect use of <label for=FORM_ELEMENT>` whenever a question is a composite/grouped control (`rating`, `grid`, `checkbox`, `radio`, `file`, `product`), because no single DOM element carries `id={`field-input-${field.id}`}`.
  - *Architectural Distinction (Single Control vs Group Legend)*:
    1. Single input controls (`hasSingleInput = ['text', 'email', 'number', 'textarea', 'select', 'date', 'time']`): Render `<Label htmlFor={`field-input-${field.id}`} id={`field-label-${field.id}`}>` and ensure the target control or trigger button (including `DatePicker` and `TimePicker`) carries `id={`field-input-${field.id}`}`.
    2. Composite/Grouped controls (`checkbox`, `radio`, `rating`, `grid`, `file`, `product`): Render the question title as `<span id={`field-label-${field.id}`} className="...">` without `htmlFor`. Wrap the options container in `role="group"` (or `<RadioGroup>`) with `aria-labelledby={`field-label-${field.id}`}` so assistive tech reads the question title, while each individual option retains its own explicit `<Label htmlFor={optionId}>` pointing directly to its sub-control.
17. *Naive Comma Splitting in Date Parsers & the JavaScript "2001" Year Default Trap*:
  - *Root Cause of Year 2001*: When attempting to strip trailing time from Google Sheet timestamp cells (e.g. `"18/10/2026, 04:15 PM"`), splitting naively on comma via `if (str.includes(',')) str = str.split(',')[0]` introduces a catastrophic bug for standard formatted English date strings. In English dates (e.g. `"October 8, 2026"`), the comma sits between the day and the year. Splitting on comma truncates `, 2026`, leaving only `"October 8"`.
  - *ECMAScript / V8 Date Fallback*: When the JavaScript V8 engine parses a month and day without a year (e.g. `new Date("October 8")`), it falls back to year 2001 (`Sun Oct 08 2001 00:00:00 GMT+0800`). Consequently, any downstream component or idempotent formatter call (such as `<CertificateTemplate>` or the preview subtitle) inadvertently renders `October 8, 2001` or `October 7, 2001`.
  - *Solution (Pattern-Based Time Stripping)*: Never use blind comma splitting. Instead, target time substrings strictly using pattern-based replacement:
    `str.replace(/,?\s*\b\d{1,2}:\d{2}(?::\d{2})?(?:\s*[AaPp][Mm])?.*$/, '').trim()`
    This strips `, 04:15 PM` or ` 16:30` while leaving `, 2026` intact, guaranteeing full idempotency for all standard date formats.

18. *Certificate Check Column Resolution & Contextual Error Design (`isEmailHeader` & `missingField`)*:
  - *Root Cause of Missing Email Column False-Negatives*: In `checkCertificateByICOrEmail`, matching email columns via `lower === 'email'` or `lower.includes('emel')` fails to match common compound spreadsheet headers such as `"Email Address"`, `"Alamat Email"`, or `"Email Peserta"` (since `includes('email')` was omitted). This causes `google-spreadsheet` lookup to abort and return `"Email field not found in Google Sheet"` even when the spreadsheet actually contains an email column.
  - *Resilient Header Detection*: Implement `isEmailHeader` (`lib/certificates/headers.ts`) covering all Malay and English variants (`email`, `e-mel`, `e-mail`, `emel`, `mail`, `alamat emel`, `email address`, and `/\b(email|emel|mail)\b/i`). Provide fallback resolution against the form definition schema (`form.fields.find(f => f.type === 'email')`).
  - *Contextual Guidance over Raw Developer Errors*: Avoid dumping raw database errors into generic red alert boxes. Return structured metadata (`missingField?: 'email' | 'ic' | 'name'`). If a participant searches by email on an IC-only event, render a helpful contextual notice ("Rekod pendaftaran bagi borang ini menggunakan Nombor Kad Pengenalan sebagai pengenalan utama") with a 1-click action button `[ Gunakan Nombor Kad Pengenalan ]` that clears the input and focuses the cursor.

19. *`@dnd-kit/sortable` Scale Distortion & DragOverlay (`CSS.Translate` vs `CSS.Transform`)*:
  - *Root Cause of Ghost Preview Distortion*: In `@dnd-kit/sortable`, using `CSS.Transform.toString(transform)` computes an aspect ratio scaling vector (`scaleX`, `scaleY`) based on height discrepancy between dragged and hovered items. When dragging a compact ~40px Page Break element over a ~250px Question Card, `@dnd-kit` applies a massive vertical scale multiplier (~600% - 700%), warping lines and text into an accordion-like distorted preview.
  - *Aspect-Ratio Preservation via `CSS.Translate`*: Use `CSS.Translate.toString(transform)` instead of `CSS.Transform.toString(transform)` on all sortable list items. `Translate` applies only translation coordinates `translate3d(x, y, 0)` without scaling, preserving the element's natural geometry regardless of neighbor heights.
  - *Solid Container & `<DragOverlay>` UX*: An uncontained or transparent element allows text from cards below to bleed through during dragging. Wrap the element in an opaque card (`bg-white border-2 border-dashed border-primary/35 rounded-2xl`) and render an elevated `<DragOverlay dropAnimation={null}>` (`shadow-2xl ring-4 ring-primary/15 cursor-grabbing`) inside `<DndContext>`, providing a buttery smooth, professional drag-and-drop ghost preview.

20. *Contextual Inline Insertion for Form Builders vs Trailing Append*:
  - *Root Cause of Drag Fatigue in Long Forms*: Restricting the addition of structural elements (like Page Breaks or Section Separators) exclusively to a global button at the bottom of the form forces users editing long forms ($> 10$ questions) to scroll all the way down, append the element to the tail, and drag it all the way up through dozens of cards.
  - *Dual-Placement Contextual Triggers*: Expose insertion points directly on each item: (a) In the card header (`CardHeader`) alongside element actions (Duplicate, Delete) for immediate 1-click access; (b) At the bottom of the card content (`CardContent`) as an inline shortcut for users who just finished configuring options or validation.
  - *Neighbor Guard (`hasNextPageBreak`)*: Dynamically check the subsequent field (`allFields[index + 1]?.type === 'pagebreak'`). When a pagebreak is already positioned immediately below, flip the action button into an informative badge (`✓ Pemisah Aktif`) to prevent accidental duplicate consecutive breaks.

21. *Multi-Day Certificate Mode Configuration (`daily_only` vs `full_only` vs `both`)*:
  - *Root Cause of Forced Combined Certificates*: In multi-day check-in/out events (`totalDays > 1`), automatically generating both daily certificates (`Hari 1`, `Hari 2`) and a combined certificate (`Semua Hari (Penuh)`) creates operational mismatches for organizers whose event policies only permit one format (e.g. modular workshops that only issue per-day certificates without a full certificate, or multi-day conventions that only issue 1 single full certificate without daily fragments).
  - *Configurable MultiDayCertMode*: Introduce `multiDayCertMode?: 'both' | 'daily_only' | 'full_only'` in `CheckInOutConfig` (persisted seamlessly in `forms.attendance_settings` JSONB).
    1. `daily_only` (Default for multi-day): `buildDailyCertificateOptions` returns strictly `[Hari 1, Hari 2, ...]`, never synthesizing `Semua Hari (Penuh)`.
    2. `full_only`: Returns strictly `[Semua Hari (Penuh)]`. On `/check/[formId]`, detecting `dailyCertificates.length === 1` naturally bypasses multi-day tab rendering and outputs the unified certificate directly with the complete event date range.
    3. `both`: Emits `[Hari 1, Hari 2, ..., Semua Hari (Penuh)]` for events where attendees are granted individual modular and complete certificates.
  - *Zero-Overhead Builder UX*: Render a responsive 3-option card selector in Form Builder Attendance Settings immediately below "Program Duration" when `totalDays > 1`. Defaulting to `daily_only` ensures that "Semua Hari (Penuh)" only appears when the user explicitly desires it ("kalau user nak baru ada").

- **Multi-Day 1-QR Attendance Architecture & Google Sheets Dynamic Columns**: When expanding a single check-in/check-out form system to support multi-day events using a single QR code:
  1. *Database non-destructive compound indexing*: Rather than adding duplicate columns (`check_in_day_2`, etc.) to a single row or requiring new forms per day, maintain normalized records where each day is an independent row tagged with `day_number integer NOT NULL DEFAULT 1` and compound index `(form_id, identifier_value, day_number)`. Single-day events naturally default to `day_number = 1` with 100% backward compatibility.
  2. *Active check-in priority over cumulative check*: In certificate gating (`checkCertificateAttendanceEligibility`), always verify if ANY record in the array is currently `checked_in` (`!r.checkOutAt`) FIRST before evaluating total completed hours. If a participant has completed Day 1 (e.g. 5 hours) and checks into Day 2 but attempts to claim their e-certificate before Day 2 ends, simply checking `completedRecords` would prematurely grant the certificate based on Day 1. Checking `activeCheckIn` unconditionally flags the status as `not_checked_out`, forcing the participant to complete their active day session.
  3. *Dynamic sheet column expansion for Multi-Day*: `updateSheetRow` dynamically appends new headers via `sheet.setHeaderRow([...headers, ...missingHeaders])`. By tagging Day 2+ columns as `Masa Masuk (Hari 2)`, `Masa Keluar (Hari 2)`, `Jumlah Jam (Hari 2)` while keeping primary cumulative summary columns (`Jumlah Masa Hadir`, `Jumlah Jam Keseluruhan (Total Hours)`), organizers get both an at-a-glance overview and day-by-day auditable timestamps without any manual spreadsheet setup.
  4. *1-Click Day K+1 Check-In*: By keeping the participant identifier in localStorage after intermediate day checkouts, the public form automatically recognizes returning attendees upon rescanning the QR on subsequent days. Instead of forcing them to refill registration fields, present an immediate, thumb-friendly `[ Check-In for Day X Now ]` action that registers Day $X$ atomically.


- **CSS 3D Transforms Context Flattening (`overflow`, `filter`, `clip-path`)**: When building 3D spatial scenes using CSS transforms (`preserve-3d` and `rotateY` on nested hierarchies), applying `overflow: hidden`, `overflow: scroll`, `filter`, `clip-path`, `opacity < 1` (on certain engines), or `backdrop-filter` to ANY ancestor element of the 3D container immediately collapses the 3D rendering context into a flat 2D plane (flattening). To preserve true 3D spatial rotation (such as book pages swinging through 3D space with `perspective: 2600px`), ancestor viewports must remain completely free of clipping/filtering properties. Page-level clipping (`overflow: hidden`) must only be applied strictly to the individual page face leaves (`.face.front`, `.face.back`) inside the sheet.

- **Dynamic Canvas Scale Hydration Mismatch (`typeof window !== 'undefined'`)**: In Next.js App Router Client Components, never branch state initialization or scale calculations on `typeof window !== 'undefined'` (e.g. `useState(() => window.innerWidth < 768 ? ... : {0, 0})`). Because SSR renders with `window === undefined` while client hydration executes with `window.innerWidth`, the server generates HTML with fallback dimensions (e.g. 374px / 33%) while the client hydrates with device dimensions (e.g. 424px / 38%), causing React 19 to fail with `Hydration failed because the server rendered text didn't match the client`. To eliminate this permanently: (1) Initialize container size state to `{ width: 0, height: 0 }` identically across both server and client; (2) Use a `mounted` state (`useState(false)` flipped in `useEffect`) and compute pre-mount scale against a stable deterministic baseline; (3) Measure actual viewport dimensions and update state strictly within `useEffect`; (4) Apply `!mounted ? 'transition-none'` so the post-hydration scale update snaps into place without visual delay or glitch; (5) Equip dynamic canvas containers and zoom percentage text with `suppressHydrationWarning`.


- **HTML2Canvas Visibility Quirk**: Never trust `html2canvas` to correctly paint elements positioned at `-9999px` out of the browser viewport. However, **never physically move** the hidden element into the active viewport using hacks like `position: fixed` and `z-index: 9999` before capturing, as this causes the enormous element to flash/spill visually across the user's screen during the 100ms it takes to snapshot. Kira dimensi kontena bingkai pentas berasaskan nisbah sebenar yang dikesan tersebut (`detectedRatio || page.aspectRatio || defaultRatio`) supaya sempadan dokumen bertepatan tepat dengan imej tanpa sebarang jurang jalur putih.
- **Single-Page Edge-to-Edge Flush Sizing & Margin Elimination**:
  1. *Elakkan Pengurangan Kelebaran Tiruan*: Dalam mod 1 Halaman (Single Page) terutamanya untuk risalah landskap atau slaid digital, jangan mengenakan pemotongan kelebaran sebarangan seperti `targetW > availW * 0.94`, `maxWidth: '96vw'`, atau menolak ruang `availW = containerWidth - 24`. Pengurangan bertingkat ini mengecilkan saiz paparan sebanyak 10% hingga 15%, lalu meninggalkan jurang kosong (gap ~50px) di sisi kiri dan kanan skrin telefon/komputer riba. Sebaliknya, benarkan `targetW` memanfaatkan 100% ruang `singleAvailW = containerDimensions.width`.
  2. *Ketinggian Anjal & Pengesanan Bucu Sempadan*: Penolakan ketinggian `availH` mestilah anjal (`containerHeight - 44` untuk landskap) kerana elemen `main` pemapar lazimnya sudah pun mengecualikan palang atas header. Sekiranya kelebaran dokumen hampir memenuhi skrin (dalam lingkungan 64px) dan ketinggian masih muat, luaskan dokumen secara terus kepada `targetW = singleAvailW` supaya gambar melekat rapat ke tepi (*edge-to-edge*).
  3. *Penyesuaian Visual Kontena Edge-to-Edge*: Apabila gambar melebar rapat ke tepi skrin (`bookWidth >= containerDimensions.width - 4`), tukar kelas bingkai daripada `rounded-xl sm:rounded-2xl` kepada `rounded-none`, dan buang bayangan tulang belakang (`spine crease shadow`) di sebelah kiri bagi dokumen landskap kerana risalah grafik/slaid adalah helaian rata dan bukannya novel berjilid.
- **FOUC Layout Shift & Mount Flash Prevention on Page Refresh**:
  1. *Punca Asal Lompat Saiz ("kenapa bila refresh dia macam ni dulu")*: Pada komponen klien yang dimensinya bergantung kepada ukuran viewport/kontena (`containerRef.current.clientWidth/clientHeight`) dan pengesanan nisbah imej (`img.naturalWidth/naturalHeight`), render permulaan (SSR dan first paint) terpaksa bergantung kepada nilai rujukan deterministik (cth: `1024x768`) dan nisbah lalai (A4 1.414). Apabila pengguna menekan muat semula (refresh / F5), pelayar merender pas pertama dengan nilai lalai ini dahulu sebelum `ResizeObserver` membaca saiz sebenar dan sebelum imej selesai dimuat turun. Perbezaan ini menghasilkan kelipan saiz visual (FOUC / layout snap) di mana kontena kelihatan kecil/bermargin sebelum tiba-tiba mengembang.
  2. *Pencegahan Menerusi `isMounted` & Pengekstrakan Cache Segera*: Jangan paparkan kontena yang belum selesai diukur pada kelegapan 100%. Mulakan komponen dengan state `isMounted = false` dan pasang kelas `transition-opacity duration-200` bersama `opacity-0 pointer-events-none`. Di dalam `useEffect` pertama: (a) Lakukan `updateSize()` serta-merta; (b) Imbas semua elemen `img` dalam kontena untuk mengekstrak `naturalWidth / naturalHeight` bagi imej yang telah sedia ada di dalam cache pelayar (`img.complete`); (c) Aktifkan `setIsMounted(true)`. Kaedah ini memastikan dokumen hanya memudar masuk (*fade-in*) ke skrin selepas saiz sebenar dan nisbah aspek telah siap dikira sepenuhnya, menghapuskan sebarang gegaran atau lompatan saiz.
- **Default Visual Theme Alignment Across System Layers**:

- **Balanced Desktop Studio Sizing & Floating Toolbar Clearance Guard**:
  Jangan memaksakan penyesuaian *edge-to-edge* 100% pada skrin lebar komputer desktop/laptop (`targetW = 100%`). Pada skrin beresolusi tinggi (1080p / 1440p) atau nisbah 16:9, regangan 100% lebar menjadikan ketinggian dokumen melonjak secara berkadar sehingga melimpah ke bahagian paling bawah tetingkap. Ini menyebabkan palang navigasi bawah terapung (`absolute bottom-4`) menutupi teks, jadual, dan ilustrasi di bahagian kaki dokumen ("zoom sangat"). Penyelesaian reka letak seimbang:
  (1) Berikan kelegaan menegak minimum 104px (`containerDimensions.height - 108` pada desktop) supaya tapak dokumen berhenti sekurang-kurangnya 30-40px di atas palang navigasi bawah;
  (2) Kenakan had kelebaran santai (`Math.min(width * 0.90, width - 64)`) dan padding pentas `p-2 sm:p-4 md:p-6` agar dokumen kelihatan seperti karya berbingkai anggun di atas kanvas studio galeri dengan bayangan lembut (`shadow-2xl rounded-xl sm:rounded-2xl`);
  (3) Serahkan pembesaran terperinci kepada gestur dwi-klik (1.85x) atau butang zum `[+]` pada toolbar apabila pengguna mahu meneliti teks halus secara khusus.
- **3D Flipbook Lighting & Shadow Elegance (Pencegahan Denyutan / Pulse Artifacts)**:
  Jangan sesekali menggunakan keyframe bayangan melantun seperti `animate={{ opacity: [0, 0, 0.25, 0] }}` atau lonjakan permulaan mendadak `initial={{ opacity: 0.3 }}` pada halaman tapak statik semasa animasi selakan 3D. Perubahan kelegapan mendadak pada muka surat yang sepatutnya pegun menghasilkan ilusi denyutan visual (*visual pulse*) atau kilatan hitam (*strobe flash*) di mata pengguna. Prinsip fizik selakan 3D realistik:
  (1) **Halaman Tapak Kekal Bersih**: Halaman tapak statik tidak memerlukan lapisan bayang buatan yang berdenyut; kedalaman optik sudah mencukupi menerusi bayangan lipatan tulang buku kekal (`spine crease shadow`);
  (2) **Pencahayaan Kertas Lembut & Gradual**: Helaian berputar (`turningLeaf`) hanya memerlukan pencahayaan kelegapan lembut ($\le 0.15$ berbanding $0.35 - 0.40$) menggunakan gradien halus `via-black/5 to-black/15` untuk membayangkan sudut terpesong dari sumber cahaya, dan mencerah kembali secara eksponen ke 0 apabila mendarat rata;
  (3) **Bayangan Helaian Sederhana**: Gantikan `shadow-2xl` (jejari 50px) dengan `shadow-lg` pada helaian berputar bagi mengelakkan sempadan bayangan tebal terpotong (*clipped*) dalam ruang perspektif 3D atau meletup hilang (*pop out*) secara mengejut sebaik sahaja helaian dinyah-lekap pada akhir animasi (t = 520ms).
- **Penghapusan Menyeluruh Punca Pulse & Pop Pada 3D Flipbook**:
  Apabila pengguna melaporkan animasi terasa seperti "keluar macam pulse", semak 5 faktor serentak dan elakkan hanya membaiki lapisan bayang:
  (1) **Bunyi Sintesis Audio**: Sintesis Web Audio API (letusan white noise 80ms) yang dipanggil tanpa syarat akan didengari oleh pengguna pembesar suara/headphone sebagai denyutan bunyi ("pop/pulse") setiap kali klik; sentiasa sekat dengan prop `soundEnabled` (lalai senyap);
  (2) **Animasi Selakan 1 Halaman**: Jangan gunakan animasi luncur sisi `x: '-105%'` dan `opacity: 0` bersama pertukaran imej tapak segera di t=0. Bina selakan kad 3D dwi-muka sejati (*True 3D Double-Sided Card Flip*) yang berputar 180 darjah pada `transformOrigin: 'center center'` dengan muka hadapan (muka surat asal) dan muka belakang (muka surat sasaran) berasingan (`backface-visibility: hidden`). Tapak di bawah kekal memaparkan muka surat asal sehingga tamat pusingan;
  (3) **Perspektif 3D Tinggi (5000px)**: Nilai perspektif 2000px/2500px menyebabkan bucu helaian mengembang sebanyak 25% mendekati kamera ("keluar"), menghasilkan ilusi kembung-kuncup; gunakan `perspective: 5000px` untuk kesan selakan isometrik yang tenang dan rata;
  (4) **Hapuskan Lapisan Tindanan Gelap**: Elakkan lapisan `<motion.div>` yang menganimasikan kelegapan hitam 0 -> 0.15 -> 0 semasa selakan kerana perubahan warna ini dibaca oleh retina sebagai denyutan gelombang hitam;
  (5) **Kunci Nisbah Aspek Dokumen**: Kunci `documentRatio` utama supaya `bookWidth` dan `bookHeight` tidak berubah walau 1 piksel pun sewaktu beralih muka surat, mengelakkan getaran saiz kontena.
- **Pencegahan Garis di Tengah Semasa Animasi 3D Flipbook (Spine Hinge vs Center Axis)**:
  Jangan sesekali menggunakan `transformOrigin: 'center center'` untuk animasi selakan 1 halaman 3D. Putaran 180° pada paksi tengah menyebabkan helaian menguncup menjadi garisan tegak setipis pisau (*knife-thin vertical edge*) tepat di tengah-tengah skrin apabila berada pada sudut 90° (`rotateY: -90deg`), memancarkan garisan pembahagi hodoh pada setiap selakan ("setiap helaian garis akan muncul di tengah").
  Prinsip seni bina selakan tanpa garis tengah:
  (1) **Engsel Tepi Tulang Buku (Spine-Hinged Flip)**: Kunci paksi putaran helaian tunggal pada tepi tulang buku: `transformOrigin: 'left center'`. Helaian berayun dari kanan ke kiri untuk *Next* (`rotateY: 0 -> -85deg`, `opacity: [1, 1, 0]`) dan dari tulang ke kanan untuk *Prev* (`rotateY: -85 -> 0deg`, `opacity: [0, 1, 1]`). Tiada satah yang pernah berserenjang di tengah skrin;
  (2) **Pertukaran Halaman Tapak Tanpa Hentakan**: Semasa selakan *Next*, muka surat sasaran dipaparkan serta-merta di halaman tapak bawah, membolehkan helaian berputar menyingkap muka surat baharu secara lancar tanpa sebarang kelipan atau pertukaran imej mengejut semasa selesai;
  (3) **Sifar Sempadan & Bayang Jahitan Dwi-Halaman**: Pada mod 2 halaman, buang sebarang elemen pembahagi tulang buatan (`w-2 z-40`), hapuskan sempadan dalaman (`border-r-0` dan `border-l-0`), buang `shadow-inner` daripada halaman asas, dan sekat bayangan lipatan tulang kasar bagi dokumen landskap (`!isLandscape`) agar poster/risalah melintang bercantum 100% licin (*seamless*).
- **Togol State Tri-State ('auto' | 'single' | 'double') & Bahaya Boolean Ternary Naif**:
  Apabila mengendalikan state togol yang mempunyai nilai permulaan `'auto'` bersama pilihan eksplisit `'single'` dan `'double'`, jangan sesekali menganggap nilai sebelumnya (`prev`) hanya mengandungi dua kemungkinan dengan menulis `prev === 'single' ? 'double' : 'single'`.
  Jika state bermula dengan `'auto'` dan paparan automatik sedang menghasilkan mod satu halaman (seperti dokumen 2 muka surat atau peranti mudah alih), semakan `prev === 'single'` mengembalikan `false`, lalu memaksa state menjadi `'single'`! Kerana `'single'` dan keadaan awal `'auto'` menghasilkan paparan visual yang sama (1 halaman), klik pertama menjadi "klik mati" (*dead click*) di mana tiada apa-apa berlaku pada skrin. Pengguna terpaksa menekan kali kedua untuk akhirnya mencetuskan pertukaran ke `'double'`.
  Prinsip seni bina togol tri-state kalis klik mati:
  (1) **Togol Berasaskan Status Aktif Semasa**: Nilai keadaan visual sebenar (`isCurrentlyDouble`) di dalam fungsi kemas kini state `setPageSpreadMode((prev) => ...)`: jika sedang memaparkan dwi-halaman, tukar ke `'single'`; jika sedang memaparkan satu halaman (sama ada `'single'` mahupun `'auto'`), tukar ke `'double'`. Ini menjamin klik pertama bertindak balas serta-merta dalam semua mod;
  (2) **Gating Kerelevanan Toolbar**: Jangan paparkan butang togol mod spread dwi-halaman jika dokumen hanya mempunyai 1 muka surat (`totalPages >= 2`), kerana dokumen helaian tunggal tidak mempunyai muka surat kedua untuk digandingkan.
- **Keseragaman Penskalaan Rentas Mod Paparan (Touch Slider vs 3D Flipbook) & Pengehadan Ruang Selamat**:
  Apabila menyediakan pelbagai mod paparan (seperti 3D Flipbook, Touch Slider, dan Skrol Menegak), jangan sesekali membiarkan mod selain flipbook menggunakan kelas saiz CSS mentah yang longgar seperti `max-w-[90vw]` atau `max-h-[calc(100vh-170px)]`. Pada skrin komputer riba atau semasa panel DevTools dibuka, kelas peratusan viewport ini akan mengembang secara agresif sehingga memenuhi 90% skrin, menyebabkan dokumen terasa "terlalu zoom" berbanding 3D Flipbook yang bersahaja, malah bahagian bawah dokumen melimpah ke bawah dan tertindih di sebalik toolbar navigasi terapung (`bottom-4`).
  Prinsip seni bina penskalaan konsisten rentas pemapar:
  (1) **Kongsi Formula Studio Dinamik yang Sama**: Dalam `SliderView`, gunakan pengiraan `containerDimensions` (`ResizeObserver`) yang identikal dengan `flipbook-view.tsx`: hadkan ketinggian dokumen landskap kepada maksimum 560px (dan potret 700px), serta tolak kelegaan bawah 108px (desktop) dan 88px (mudah alih) daripada ketinggian kontena supaya bar navigasi tidak sesekali bertindih dengan teks dokumen;
  (2) **Kawalan Lebar Skrol Menegak**: Dalam `VerticalView`, gunakan had kelebaran anjal `max-w-[min(90vw,780px)]` bagi landskap dan `max-w-[min(88vw,540px)]` bagi potret, serta sediakan `pb-28 sm:pb-32` pada kontena skrol supaya helaian terakhir boleh dibaca sepenuhnya dengan kelegaan selesa di atas toolbar bawah;
  (3) **Membezakan Amaran Dev Pelayan dengan Ralat Sistem**: Amaran prapemuatan pelayar (`The resource ... was preloaded using link preload but not used within a few seconds`) dan log instrumentasi Next.js (`Slow execution detected...`) di konsol DevTools pada `localhost:3000` adalah mesej diagnostik dalaman mod pembangunan Next.js/HMR, bukan ralat sistem yang merosakkan aplikasi (0 ralat sebenar).

- **Mobile Viewport Simulators & Document Orientation Adaptation**:
  Apabila membina pemapar dokumen interaktif (seperti e-pamphlet / buku program digital) yang menyokong pratonton simulator telefon di dalam pelayar desktop:
  (1) **Media Query CSS vs Bingkai Simulator**: Kelas CSS seperti `sm:inline` atau `lg:hidden` dinilai berasaskan saiz tetingkap pelayar (browser viewport), BUKAN saiz bingkai simulator anak. - **Perbezaan Seni Bina Selakan 3D: Mod 2 Halaman (Dwi-Muka Surat) vs Mod 1 Halaman (Helaian Tunggal)**:
  Apabila pengguna menyatakan "2 pages okay 3d flip, 1 page je yg problem", fahami punca geometri di sebalik perbezaan kedua-dua mod ini:
  (1) **Kenapa Mod 2 Halaman Berfungsi Sempurna**: Dalam mod 2 halaman (*two-page spread*), pentas buku mempunyai dua bahagian: halaman kiri ($[0, 50\%]$) dan halaman kanan ($[50\%, 100\%]$) dengan tulang buku di tengah ($50\%$). Helaian berputar ($50\%$ lebar) berputar 180° merentasi tulang tengah dan mendarat rapi di atas halaman kiri. Seluruh pergerakan kekal berada di dalam sempadan bingkai buku 2 muka surat.
  (2) **Punca Masalah Pada Mod 1 Halaman**: Dalam mod 1 halaman (*single page / mobile*), lebar dokumen adalah $100\%$ lebar kontena. Jika helaian diputarkan 160° - 180° berpaksi pada engsel kiri (`transformOrigin: 'left center'`), helaian berputar KELUAR daripada bingkai dokumen ke ruang kosong di sebelah kiri (malah terkeluar daripada skrin telefon ke kawasan gelap). Ini kelihatan pelik dan rosak kerana tiada halaman kiri untuk helaian tersebut mendarat.
  (3) **Penyelesaian Muktamad Mod 1 Halaman (3D Paper Curl & Peel)**: Mod helaian tunggal mesti menggunakan simulasi kelengkungan kertas 3D sejati (*authentic 3D paper curl & peel* seperti Apple Books / StPageFlip) yang kekal terkandung di dalam kontena (`overflow-hidden`):
      - Bucu helaian terangkat dalam perspektif 3D dengan putaran `rotateY: -25deg` dan kecondongan pepenjuru organik `rotateZ: -3deg` berpaksi pada `right center`.
      - Jalur bayangan kertas 3D tebal dwi-lapisan (`shadow-[-16px_0_36px_rgba(0,0,0,0.32),-6px_0_12px_rgba(0,0,0,0.2)]`) mengekori lipatan selakan dan jatuh ke atas muka surat baharu di bawah.
      - Kilauan silinder 3D (*cylindrical highlight sheen* `from-white/60 via-black/10 to-transparent`) membiaskan cahaya di sepanjang permatang lengkungan kertas.
      - Helaian menyapu licin dari kanan ke kiri (`x: 0 -> -102%`) dan bergulung kemas ke dalam tulang kiri, menyingkap halaman baharu di bawahnya tanpa sebarang pembengkakan kamera, tanpa terpelanting keluar skrin, dan sifar garisan tengah.

- **Penghapusan Glitch Visual Selepas Animasi 3D Flip (Seamless Frame-Perfect Handoff & Shadow Dissolve)**:
  Apabila pengguna melaporkan "bila lepas 3d flip tu rasa macam ada glitch sikit", ini berpunca daripada 5 isu serentak sewaktu helaian selakan dinyah-lekap (*unmounted*):
  (1) **Lonjakan Transformasi `targetShiftX`**: Menetapkan `targetSpreadRef.current = null` secara segerak di dalam `onFlipAnimationComplete` menyebabkan `targetShiftX` membaca `activeSpread` (spread lama) sebelum render baharu berlaku, mencetuskan lonjakan sekejap pada koordinat paksi X kontena. Gunakan `requestAnimationFrame` untuk memastikan rujukan spread sasaran kekal aktif sehingga render keadaan baharu telah selamat dikomit;
  (2) **Pertukaran Mendadak `img.src` Halaman Tapak (*Decode Flash*)**: Apabila helaian selakan dinyah-lekap serentak dengan arahan menukar `src` pada elemen `<img>` halaman tapak di bawahnya, pelayar memerlukan 1 frame untuk mendekod bitmap baharu, menyebabkan kelipan kosong/putih seketika. Selesaikan dengan memasang imej sasaran terlebih dahulu secara tersembunyi (*pre-mounted target image*) di dalam kontena tapak dari detik awal selakan (t=0), dan tangguhkan nyah-lekap helaian selakan sebanyak 1 frame menerusi `requestAnimationFrame` agar halaman tapak telah sedia terpapar sepenuhnya sebelum helaian diangkat;
  (3) **Penyelarasan Bayangan Helaian (*Drop-Shadow Dissolve*)**: Jangan biarkan bayangan jatuh (`drop-shadow-xl`) kekal pada intensiti penuh apabila helaian mendarat rata pada 180° / 0°. - **Penyelarasan Segerak Transisi Imej dengan Putaran 3D Flipbook (Symmetrical Midpoint Apex & Pure Peel Architecture)**:
  Apabila pengguna melaporkan "dari segi 3d flip macam okay utk 1 page dan 2 pages, cuma utk trasition gambar tu macam tak sync bila 3d flip", ini berlaku disebabkan 4 punca dinamik pergerakan imej vs putaran fizikal:
  (1) **Ketidakseimbangan Lengkungan Easing (*Easing Curve Front-Loading*)**: Penggunaan lengkungan ease-out mendadak seperti `cubic-bezier(0.25, 1, 0.5, 1)` menyebabkan putaran melepasi sudut 90° dalam ~75ms pertama daripada tempoh 520ms animasi (iaitu hanya pada 15% masa). Akibatnya, imej muka hadapan hilang serta-merta pada permulaan selakan dan bertukar kepada imej belakang, manakala helaian itu sendiri mengambil baki 445ms untuk perlahan-lahan mendarat. Pengguna melihat ini sebagai pertukaran imej yang "terlalu awal / tak sync dengan pusingan". Penyelesaian: Gunakan lengkungan masa simetri `cubic-bezier(0.45, 0.05, 0.55, 0.95)` di mana titik putaran 90° (apex berserenjang) dicapai tepat pada 50% masa selakan (260ms). Muka hadapan dan muka belakang masing-masing kelihatan selama 260ms, menyelaraskan pertukaran imej tepat di puncak pusingan 3D;
  (2) **Pemisahan Kedalaman Mikro (*translateZ(1px) anti-Z-Fighting*)**: Pada satah 3D dwi-muka surat di mana muka hadapan (`rotateY: 0deg`) dan muka belakang (`rotateY: 180deg`) berkongsi kedalaman $Z = 0$, enjin rasterisasi WebKit/Blink mengalami *Z-fighting* di mana piksel muka belakang bocor sebelum waktunya. Tambahkan `translateZ(1px)` pada kedua-dua permukaan untuk memastikan peralihan visual muka surat dipotong tepat pada sudut 90°;
  (3) **Penyingkiran Tag `<img>` Bertindih Pendua di Halaman Tapak**: Menambah tag `<img>` kedua secara serentak di dalam kontena tapak bagi tujuan "pre-mount" menyebabkan fenomena bayangan berganda (*ghosting*) dan pertindihan rendering telus. Sebaliknya, gunakan prapemuatan cache di latar belakang (`new Image().src = url`) dalam `useEffect` tanpa menyentuh pohon DOM;
  (4) **Kesimetrian Mengupas Helaian Mod 1 Muka Surat (*Symmetrical Pure Peel*)**: Dalam mod 1 muka surat, selakan NEXT dan PREV mesti beroperasi mengikut prinsip yang sama:
      - NEXT: Halaman tapak bersedia dengan `nextPage`, helaian semasa mengupas ke kiri (`x: 0% -> -105%`, `rotateY: -25deg`, paksi kanan), mendedahkan `nextPage` di bawahnya.
      - PREV: Halaman tapak bersedia dengan `prevPage`, helaian semasa mengupas ke kanan (`x: 0% -> 105%`, `rotateY: 25deg`, paksi kiri), mendedahkan `prevPage` di bawahnya.
      Kedua-dua arah memaparkan muka surat destinasi pada lapisan tapak sejak $t=0$, menjadikan penyingkapan gambar 100% seiring dan segerak dengan pergerakan helaian fizikal.

- **Penyelarasan Mutlak Transisi Imej 2 Halaman (Two-Page Spread Synchronization & Pure 3D Context Integrity)**:
  Apabila pengguna menyatakan "utk 1 page dh okay, utk 2 pages ni macam tak okay sikit, bila 3d flip gambar tak berapa nk sync", fahami punca fizikal dan visual yang khusus pada susun atur dwi-halaman:

Gunakan animasi `boxShadow` pada elemen muka hadapan dan belakang yang melarut licin ke 0px apabila helaian mendarat rata;
  (2) **Perangkap Lengkungan Easing Terlalu Curam**: Lengkungan seperti `[0.45, 0.05, 0.55, 0.95]` mempunyai nisbah cerun $\Delta y / \Delta x = 0.90 / 0.10 = 9.0$ di tengah animasi. Ini memecutkan putaran daripada 9° ke 171° dalam hanya 50ms, menyebabkan imej kelihatan seperti menyentap mendadak dan tidak selari dengan selakan tangan manusia. Gantikan dengan lengkungan fizik klasik yang anggun `cubic-bezier(0.42, 0, 0.58, 1)` dengan tempoh 540ms dan selaraskan peralihan CSS anjakan kontena (`transform 540ms cubic-bezier(0.42, 0, 0.58, 1)`) agar kedua-duanya bergerak seirama;
  (3) **Prapemuatan Menyeluruh Mengikut Unit Spread (*Spread-Aware Preloading*)**: Dalam mod 2 halaman, setiap kali selakan berlaku, pergerakan melangkau 2 muka surat. Prapemuatan ringkas `currentPage ± 2` gagal memuat turun muka surat kedua spread berikutnya (`currentPage + 3`). Prapemuat kesemua halaman bagi risalah bersaiz sederhana ($\le 16$ halaman) atau $\pm 5$ halaman ke hadapan/belakang bagi risalah besar agar imej sentiasa 100% berada dalam memori pelayar sebelum butang ditekan;
  (4) **Pembalikan Geometri Muka Belakang (*Back Face Geometric Inversion*)**: Apabila muka belakang diputarkan 180° dan mendarat di sebelah kiri (selakan NEXT), bucu luar berada di sisi kiri (`rounded-l-2xl border-l`) dan bayangan lipatan tulang buku berada di sisi kanan (`right-0 bg-gradient-to-l`). Sebaliknya pada selakan PREV, bucu luar berada di sisi kanan (`rounded-r-2xl border-r`) dan bayangan tulang di sisi kiri (`left-0 bg-gradient-to-r`);
  (5) **Kawalan Nullish Halaman Tapak Semasa Menutup Buku**: Elakkan operator fallback `targetSpreadRef.current?.leftPage ?? activeSpread.leftPage` kerana semasa menutup buku ke kulit hadapan, `leftPage` sengaja bernilai `null`. Fallback yang salah akan memaparkan halaman lama di atas meja sewaktu helaian diangkat, mencetuskan fenomena helaian pendua (*duplicate page flash*). Gunakan `isLeftBaseHidden` dan `isRightBaseHidden` untuk menyembunyikan halaman tapak dengan bersih.

- **Spesifikasi Ketat HTML5 `<input type="color">` & Penghapusan Amaran "The specified value does not conform to the required format"**:

      ```ts
      export function toValidHexColor(color: string | undefined | null, fallback = '#000000'): string {
        if (!color || typeof color !== 'string') return fallback;
        const trimmed = color.trim().toLowerCase();
        if (['transparent', 'none', 'inherit', 'initial', 'unset'].includes(trimmed)) return fallback;
        if (/^#[0-9a-f]{6}$/.test(trimmed)) return trimmed;
        if (/^#[0-9a-f]{3}$/.test(trimmed)) return `#${trimmed[1]}${trimmed[1]}${trimmed[2]}${trimmed[2]}${trimmed[3]}${trimmed[3]}`;
        if (/^#[0-9a-f]{8}$/.test(trimmed)) return trimmed.substring(0, 7);
        if (/^[0-9a-f]{6}$/.test(trimmed)) return `#${trimmed}`;
        if (/^[0-9a-f]{3}$/.test(trimmed)) return `#${trimmed[0]}${trimmed[0]}${trimmed[1]}${trimmed[1]}${trimmed[2]}${trimmed[2]}`;
        return fallback;
      }
      ```

- **Supabase Auth Duplicate Signup Trap & Anti-Enumeration (`identities.length === 0`)**:
  - *Root Cause of Missing Signup Emails*: When a user attempts to sign up via `supabase.auth.signUp()` with an email that is already registered in `auth.users` (for example, previously registered via Google OAuth), Supabase returns `{ data: { user: ..., session: null }, error: null }` where `data.user.identities` is an empty array (`[]`). Supabase intentionally suppresses the error and **DOES NOT SEND ANY CONFIRMATION EMAIL** to prevent malicious email enumeration.
  - *Frontend Trap*: If frontend authentication code only checks `if (error)` and assumes `else` means a successful registration, it flashes a misleading *"Account created! Please check your email"* message. The user waits indefinitely for an email that was never dispatched.
  - *Standard Solution*: Always inspect the returned identities array:
    ```ts
    const { data, error } = await supabase.auth.signUp(...);
    if (error) {
      toast.error(error.message);
    } else if (data?.user?.identities && data.user.identities.length === 0) {
      // Email is already registered
      toast.error('Emel ini telah pun berdaftar. Sila log masuk atau gunakan "Continue with Google".');
      setActiveTab('login');
    } else if (data?.session) {
      // User auto-confirmed
      router.push('/forms');
    } else {
      setSignupSuccess(true);
    }
    ```
